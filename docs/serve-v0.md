# hn serve v0: governed local Git hosting

## Overview

`hn serve` turns an unprivileged Unix account into a Git host for Hubnot
repositories. OpenSSH authenticates each connection and runs a forced `hn serve`
command, which maps the SSH key to a Hubnot actor and checks every pushed ref
update before Git moves it. The service is optional: no other `hn` command
depends on it, and clients that push to ordinary Git remotes see no change. The
replication rules it reuses are described in
[replication-v0.md](replication-v0.md), and the trust boundaries in
[threat-model.md](threat-model.md). The
[Verification and traceability](#verification-and-traceability) section maps
each requirement to the tests that check it.

## Server account and state layout

Run `hn serve` as a dedicated, unprivileged user, for example one created with
`useradd --create-home --shell /bin/sh hn`. All server state belongs to that
account and lives in its home directory. `hn serve` writes only below
`$HOME/.hn-serve/` and to `$HOME/.ssh/authorized_keys`.

Every `hn serve` command checks the effective user ID before it reads `HOME` or
any file. When the command runs as root it stops with:

```text
hn: hn serve refuses to run as root; create an unprivileged user for the server
```

The server home has one fixed layout:

```text
$HOME/
├── .ssh/                       0700, created if absent
│   └── authorized_keys         0600; managed block plus administrator lines
└── .hn-serve/                  0700
    ├── hooks/                  0700, regenerated by every administration command
    │   ├── pre-receive         0700 script: exec ABS_HN serve hook pre-receive
    │   └── post-receive        0700 script: exec ABS_HN serve hook post-receive
    ├── repositories/           0700
    │   └── NAME.git/           bare repository created by hn serve repo create
    └── state/                  0700
        ├── registry.json       0600
        ├── tmp/                0700, TMPDIR for Git and hooks
        └── repos/              0700
            └── NAME/           0700
                ├── config.json     0600
                ├── branches.json   0600, absent until the first owned branch
                ├── push.log        0600, append-only JSON Lines
                ├── lock            0600, flock target for pushes
                ├── lfs.lock        0600, flock target for LFS commits
                └── lfs/            0700
                    ├── incoming/   0700, staged uploads
                    └── objects/    0700, verified objects in OID[0:2]/OID[2:4]/OID
```

`registry.json` binds SSH key fingerprints to actors. `config.json` holds one
hosted repository's protected branches, LFS quota and push budgets.
`branches.json` records which actor created each ordinary branch. `push.log`
records one JSON object per push for operators; the server never reads it back.
The exact file formats are in the
[server-state contract](../kitty-specs/hn-serve-01M5P0NP/contracts/server-state.md).

A repository name starts with a letter or digit, continues with letters,
digits, `.`, `_` or `-`, is at most 100 characters long, never contains `..` and
never ends in `.git`. The bare repository for `NAME` is always
`repositories/NAME.git`.

### What makes the server refuse to run

Each `hn serve` command validates the whole layout before it does anything else.
The first defect stops the command with a message that names the path, in the
form `hn: hn serve state defect: PATH: REASON`. Validation walks names in sorted
order, so the same defect always produces the same message. The server refuses
to run when it finds any of the following:

- a symbolic link anywhere in the layout, including a symlinked `.ssh`
  directory or a symlinked `repositories/NAME.git`;
- a directory whose mode is not 0700, or a state file whose mode is not 0600
  (hook scripts must be 0700); the message reports the observed mode. This
  includes each `repositories/NAME.git` directory itself. Validation does not
  look inside a bare repository, but its top directory must be 0700;
- an entry the layout does not define in `.hn-serve/`, `hooks/`, `state/`,
  `state/repos/`, `state/repos/NAME/` or `lfs/`, or an entry in
  `repositories/` that is not `NAME.git` for a valid name;
- a `state/repos/NAME/` without a matching `repositories/NAME.git/`, or the
  reverse;
- a missing `config.json` for a hosted repository;
- a JSON state file with an unknown field, trailing data, a value that breaks
  its rules, or a size above 16 MiB;
- a `push.log` above 64 MiB;
- a hook script that is missing or whose bytes differ from the generated
  script;
- inside `state/tmp/`, `lfs/incoming/` and `lfs/objects/`, any symbolic link,
  device, socket or named pipe, any directory that is not 0700, any file that is
  not 0600, or more than 100,000 entries in one of those subtrees.

The checks inside `state/tmp/` and the LFS directories do not read file
contents or apply name rules, because those directories hold transient and
content-addressed files. Administration commands may keep their own lock files
in `state/tmp/`.

An interrupted state write can leave a temporary file such as
`state/.hn-private-1234` behind. Validation reports it as an unexpected entry;
remove it and rerun the command. An administration command that stops while it
rewrites a hook can leave a staging file such as `hooks/.hn-hook-1234`.
Validation reports it as an abandoned hook staging file; remove it, then run any
`hn serve repo` or `hn serve key` command to regenerate the hooks. The push log grows by one line per push. Archive
or truncate it before it reaches 64 MiB.

### Administration commands and sessions

Administration commands (`hn serve repo ...` and `hn serve key ...`) create any
missing directory in the layout with mode 0700, then rewrite both hook scripts
for the `hn` binary that is running, then validate. Every one of them does this,
including the read-only `hn serve repo list`, `hn serve repo show NAME` and
`hn serve key list`, so running `hn serve repo list` is a quick way to prepare a
new server account and to check an existing one. Session commands
(`hn serve git` and the internal `hn serve hook`) only read: a missing directory
or a stale hook script makes them refuse.

Each hook script is two lines that run the absolute, symlink-resolved path of the
`hn` binary:

```sh
#!/bin/sh
exec /usr/local/bin/hn serve hook pre-receive
```

After you move or upgrade `hn`, run any `hn serve repo` or `hn serve key`
command to regenerate the hooks and the `authorized_keys` block. Until then,
every fetch and push refuses with a hook-script defect.

### Concurrent commands

Many `hn serve` commands can run at once, for example several pushes and an
administrator's `hn serve repo list`. They coordinate through an `flock(2)` lock
on the `.hn-serve` directory itself, so the layout gains no extra file.
An administration command holds the lock exclusively while it rewrites the hooks
and validates the layout. A session command holds it shared while it validates,
so sessions run side by side and never see a hook script half written. Each
command releases the lock after validation, before it does its own work.
Administration commands take it exclusively again only while they replace a
state file, and `hn serve repo create` holds it for its whole import, as
described in [Administering hosted repositories](#administering-hosted-repositories). A
command that cannot get the lock within 120 seconds stops with
`hn: hn serve layout is busy: ...`; run it again when the other command
finishes.

The hook scripts and `authorized_keys` contain the `hn` path without quotes, and
`/bin/sh` runs the hooks. `hn` therefore accepts only a clean absolute path made
of ASCII letters, digits and the characters `/ . _ - + @ , :`, none of which the
shell expands or splits. Any other character, such as `$`, a backtick, `;`, `*`,
a quote, a backslash, whitespace or a non-ASCII letter, makes every
administration command refuse before it writes a hook. Install `hn` at a path
such as `/usr/local/bin/hn` or `/home/hn/bin/hn`.

### Protected branch order in config.json

The `protected` list in `config.json` names full refs such as
`refs/heads/main`. Its first entry is the default protected branch, and the
repository's `HEAD` points to it. The remaining entries follow in byte order
with no duplicates. For example, a repository whose default branch is `trunk`
and which also protects `alpha` and `release` stores
`["refs/heads/trunk", "refs/heads/alpha", "refs/heads/release"]`.

### Locks and filesystems

Pushes to one repository are serialized with `flock(2)` on
`state/repos/NAME/lock`, and a push waits up to 120 seconds for it.
`hn serve repo lock-exec NAME -- COMMAND [ARG]...` takes the same lock, runs
`COMMAND` without a shell in the bare repository with `GIT_DIR` set to it,
releases the lock and exits with the command's status. When the lock stays busy
for the whole wait it exits 1 with a `repository-busy` message. `flock` is
not reliable on every network filesystem, so keep the server home on a local
filesystem.

## Key bindings and authorized_keys

OpenSSH authenticates every connection to the server account. `hn serve` does
not implement SSH; it decides which Hubnot actor an authenticated key belongs
to and makes sure OpenSSH runs `hn serve git` for that key and nothing else.

### What a key binding is

A key binding maps one SSH public key, identified by its full SHA256
fingerprint, to one Hubnot actor, identified by its full 64-hex actor
fingerprint. Bindings are stored in `state/registry.json`. One key binds to
exactly one actor. One actor may hold several keys, for example one per
laptop or one per security key.

A binding gives the actor two things: SSH access to the hosted repositories
and attribution of that actor's pushes. It grants no policy role. Roles such as
maintainer or verifier come only from the policy documents in each repository,
and a push from a bound key is checked against those policies like any other
(C-006).

The [Administering hosted repositories](#administering-hosted-repositories)
section shows the `hn serve key` commands that add, list and remove bindings.

### Supported key types

`hn serve` accepts these OpenSSH public key types:

- `ssh-ed25519`
- `sk-ssh-ed25519@openssh.com`
- `ecdsa-sha2-nistp256`
- `ecdsa-sha2-nistp384`
- `ecdsa-sha2-nistp521`
- `sk-ecdsa-sha2-nistp256@openssh.com`
- `ssh-rsa`

Any other type, including `ssh-dss` and every certificate type, is refused with
a message that names it.

A key is given as one line in the format of a `.pub` file or an
`authorized_keys` entry: the key type, the base64 key and an optional comment,
separated by spaces. A leading `authorized_keys` options field such as
`restrict,command="a b"` is accepted and ignored. Only the key type and base64
key are stored and written back, so options and comments from the input never
reach the server's `authorized_keys`. The line is refused when it is empty,
longer than 16 KiB, contains a tab or any other control character apart from a
single final newline, uses base64 without its `=` padding, or holds a key blob
whose embedded type differs from the type field, whose lengths run past its
end, or that carries trailing bytes.

### Fingerprints

A fingerprint is `SHA256:` followed by 43 characters of unpadded standard
base64: the SHA-256 digest of the decoded key blob. It is the value that
`ssh-keygen -l -E sha256 -f KEY.pub` prints in its second field:

```console
$ ssh-keygen -l -E sha256 -f ~/.ssh/id_ed25519.pub
256 SHA256:Mnm7DCteTtegvPg/NcGZVvsMTFM5gR+dbIBbGci5vSg alice@laptop (ED25519)
```

Every `hn serve` command that takes a fingerprint requires all 43 characters.
A shortened or otherwise malformed fingerprint is refused.

### The managed block in authorized_keys

`hn serve` writes one managed block into `$HOME/.ssh/authorized_keys` of the
server account. The block starts and ends with fixed marker lines and holds one
entry per binding, sorted by fingerprint:

```text
# BEGIN hn serve managed keys; edit with hn serve key
restrict,command="/usr/local/bin/hn serve git --key SHA256:Mnm7DCteTtegvPg/NcGZVvsMTFM5gR+dbIBbGci5vSg" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAICqPfpPz/R1uz/vd9nUpjEhAMWYVmeerTHMSJDGYgg3A hn-serve:4f1c9a6d0d2b
# END hn serve managed keys
```

Each entry has three parts:

- `restrict` turns off port, agent and X11 forwarding, PTY allocation and
  `~/.ssh/rc`;
- `command="ABS_HN serve git --key FINGERPRINT"` makes `sshd` run `hn serve git`
  with the binding's fingerprint whatever command the client asked for.
  `ABS_HN` is the absolute, symlink-resolved path of the `hn` binary that wrote
  the block. The same path rules apply as for the hook scripts, so a path with a
  quote, a backslash or whitespace is refused before anything is written;
- the key type and base64 key, followed by the comment `hn-serve:` and the
  first 12 characters of the bound actor.

A registry with no bindings still produces the two marker lines. Before it
writes an entry, `hn serve` parses the stored public key again and requires its
fingerprint to equal the binding's fingerprint, so a hand-edited registry whose
key and fingerprint disagree stops the command.

Do not edit the block by hand. Every `hn serve key` command rewrites it from
the registry, and so does every `hn serve repo` command. After you move or
upgrade `hn`, run one of them to update the command path.

### Lines outside the block

You can keep your own keys and comments in the same file. `hn serve` changes
only the lines from the begin marker through the end marker. Every byte outside
the block stays as it was, including Windows `
` line endings and a missing
final newline. When the file has no block yet, `hn serve` appends one at the
end, first adding a single `
` if the file does not already end with one. A
marker counts only when it is the whole line, without leading or trailing
spaces.

The new file is written to a temporary file in `.ssh` with mode 0600, synced
and renamed over `authorized_keys`, so `sshd` sees either the old file or the
new one. If a command is interrupted between those steps, a file such as
`.ssh/.hn-private-1234` may be left behind; remove it.

### When hn serve refuses to touch authorized_keys

`hn serve` creates `$HOME/.ssh` with mode 0700 when it does not exist. It stops
before writing anything when it finds any of the following:

- `.ssh` is a symbolic link or is not a directory;
- `.ssh` is writable by group or others, for example mode 0775;
- `authorized_keys` is a symbolic link or is not a regular file;
- `authorized_keys` is writable by group or others, for example mode 0664;
- `authorized_keys` is larger than 4 MiB;
- `authorized_keys` has two begin markers, two end markers, an end marker
  without a begin marker before it, or a begin marker without an end marker
  after it.

The message names the path and, for a mode problem, the command that fixes it,
such as `chmod 700 /home/hn/.ssh`. `hn serve` never repairs an unsafe `.ssh`
or `authorized_keys` itself, because `sshd` with `StrictModes` rejects the same
setup and a silent repair would hide the misconfiguration. An existing `.ssh`
with a safe mode such as 0755 is kept as it is. The rewritten
`authorized_keys` always has mode 0600.

## Administering hosted repositories

Every command in this section runs as the server account. The examples use
`sudo -u hn-serve` from an administrator's shell; logging in as the server
account works the same way.

### Preparing the server account

Create one unprivileged account for the server and install `hn` at a path the
hook scripts and `authorized_keys` can name, as root, once:

```sh
useradd --create-home --shell /bin/sh hn-serve
install -m 0755 ./hn /usr/local/bin/hn
```

The server needs Git 2.29 or later, because `hn serve repo create` creates
each repository in the object format of its source. Participants who use large
files need the Git LFS client on their own machines. `sshd` must allow
public-key login for `hn-serve`. With the default `StrictModes yes`, the
account's home directory and `~/.ssh` must not be writable by group or others.

Run `sudo -u hn-serve hn serve repo list` once to create the layout described
in [Server account and state layout](#server-account-and-state-layout). It
prints nothing on a new account.

### Creating a hosted repository

A hosted repository exists only after an administrator creates it. A push
never creates one, whatever repository name the client asks for. Seed it from
an existing repository whose default branch already carries
`.hn/policy.json`:

<!-- example: repo-create -->
```sh
sudo -u hn-serve hn serve repo create pingpong --from /srv/import/rust-pingpong.git
```

```text
Created hosted repository pingpong
Protected: refs/heads/main
LFS quota: 1073741824 bytes
Clone URL: ssh://hn-serve@git.example.internal/pingpong.git
```

`--from` takes a local path or any URL that `git fetch` accepts. The clone URL
is built from the server account's login name and the host name of the
machine.

`hn serve repo create` imports only branches (`refs/heads/*`) and tags
(`refs/tags/*`). It leaves behind every other ref of the source, including
Hubnot actor chains, proposals and other `refs/hn/*` refs, and `refs/notes/*`.
Hubnot facts reach a hosted repository only through governed pushes, which
validate each one, so a fact on the server has always passed the server's
checks. Objects are checked with `fetch.fsckObjects` during the import, and a
source with a malformed object is refused.

The new repository protects `refs/heads/main` unless you name other branches.
Give `--protect` once per branch, as a short name such as `release` or a full
ref such as `refs/heads/release`. The first one is the default protected
branch, and the repository's `HEAD` points to it. `--lfs-quota BYTES` sets the
Git LFS quota, which defaults to 1073741824 bytes (1 GiB). Push budgets start
at the defaults of `hn replication select`.

Each protected branch must exist in the source, and its tip must hold a
`.hn/policy.json` that `hn` can parse. A protected branch without valid policy
could never move, because every update to it is checked against that policy.
Creation is refused, with a message that names the branch and the reason, in
any of these cases:

- the name is not a valid repository name, or a repository with that name
  exists;
- a protected branch is missing from the source;
- a protected branch's tip has no `.hn/policy.json`, or one that does not
  parse;
- the source cannot be read, has no refs, or holds objects that fail the
  object checks.

The command builds the repository in a staging directory below `state/tmp/`
and moves it into `repositories/` and `state/repos/` only after every check
has passed. A refused creation therefore leaves nothing in either directory.
While it runs, it holds the layout lock, so other `hn serve` commands, pushes
included, wait for it for up to 120 seconds. If the command is interrupted,
for example with Ctrl-C during a long import, the staging directory stays
behind and every `hn serve` command refuses to run until the next
administration command removes it. Run `hn serve repo list` to clean up.

`hn serve repo create` writes no hooks and no `core.hooksPath` into the
repository. The wrapper passes the server's hooks to Git on the command line
for every push.

### Binding and removing keys

Every participant who connects needs a key binding, and that includes CI
runners and verifiers, because they publish results with `hn sync`. Each
participant sends their SSH public key file and their full actor fingerprint,
which `hn identity show` prints. Bind the key to the actor:

<!-- example: key-add -->
```sh
sudo -u hn-serve hn serve key add --actor 4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c alice.pub
```

```text
Bound SHA256:Jd8bC8QWw0m0Y4l6m6yZ1gq5q3o9s0Kc2b2f4QwA9eU to actor 4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c
```

Give `-` in place of the file name to read the key from standard input. The
input must hold exactly one non-empty line, up to 16 KiB, in the formats
described in [Supported key types](#supported-key-types); a line may end with
LF or CRLF. `--actor` must be the full 64-character lowercase actor
fingerprint. `hn serve key add` refuses a key that is already bound, to the
same actor or to another one. To move a key to another actor, remove it first.
One actor may hold several keys.

List the bindings, one per line in fingerprint order:

```sh
sudo -u hn-serve hn serve key list
```

```text
SHA256:Jd8bC8QWw0m0Y4l6m6yZ1gq5q3o9s0Kc2b2f4QwA9eU 4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c ssh-ed25519
```

Remove a binding by its full fingerprint:

```sh
sudo -u hn-serve hn serve key remove SHA256:Jd8bC8QWw0m0Y4l6m6yZ1gq5q3o9s0Kc2b2f4QwA9eU
```

```text
Removed SHA256:Jd8bC8QWw0m0Y4l6m6yZ1gq5q3o9s0Kc2b2f4QwA9eU from actor 4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c
```

The removed key is refused on its next connection. Connections that are
already open finish normally.

Both commands save `state/registry.json` first and then rewrite the managed
block in `authorized_keys`. If the second step fails, the command stops with:

```text
hn: registry updated but authorized_keys was not rewritten: CAUSE; rerun any hn serve key or repo command
```

The system stays safe in that state: a newly added key cannot connect yet, and
a removed key that connects finds no binding and is refused. Fix the cause, for
example the mode of `~/.ssh`, and run any `hn serve key` or `hn serve repo`
command to write the block.

### Listing and inspecting repositories

`hn serve repo list` prints one repository name per line in byte order.
`hn serve repo show NAME` prints its configuration:

```sh
sudo -u hn-serve hn serve repo show pingpong
```

```text
name: pingpong
path: /home/hn-serve/.hn-serve/repositories/pingpong.git
protected: refs/heads/main
lfs-quota: 1073741824
lfs-stored: 0
max-events: 10000
max-objects: 100000
max-object-bytes: 67108864
max-attachment-bytes: 16777216
max-total-bytes: 1073741824
```

There is one `protected:` line per protected branch, the default first.
`lfs-stored` is the total size of the stored Git LFS objects. The `max-` lines
are the push budgets, with the names and meaning they have in
`hn replication show`.

### Changing protected branches, quotas and budgets

`hn serve repo set NAME` changes a repository's configuration and prints it in
the `repo show` format:

```sh
sudo -u hn-serve hn serve repo set pingpong --protect release --lfs-quota 2147483648
```

- `--protect REF` protects another branch. As with `repo create`, the branch
  must exist and its tip must hold a valid `.hn/policy.json`.
- `--unprotect REF` stops protecting a branch. The last protected branch
  cannot be unprotected, and one ref cannot appear in both flags. When you
  unprotect the default branch, the next remaining protected branch becomes
  the default, and `HEAD` follows it.
- `--lfs-quota BYTES` sets the Git LFS quota.
- `--max-events`, `--max-objects`, `--max-object-bytes`,
  `--max-attachment-bytes` and `--max-total-bytes` set the push budgets. Each
  must be a positive integer, as in `hn replication select`.

Every check runs before anything is written, so a refused change leaves the
configuration as it was. The command holds the repository lock while it checks
and saves, so no push moves a branch between its policy check and the new
configuration. Each run also points `HEAD` at the default protected branch;
rerunning `hn serve repo set NAME` without flags repairs a `HEAD` that an
interrupted change left behind.

### How administration commands coordinate

Administration commands take a lock on `state/tmp/admin.lock` before they
validate the layout and hold it until they finish, so two administrators never
interleave registry or repository changes. A command that waits 120 seconds
for it stops with `hn: hn serve administration is busy: ...`.
`hn serve repo lock-exec` releases this lock before it waits for the
repository lock, so a long recovery does not block key changes.

Every administration command rewrites the managed block in `authorized_keys`
from the registry, in addition to the hook scripts. Before its own work, each
command checks `~/.ssh` and `authorized_keys` as described in
[When hn serve refuses to touch authorized_keys](#when-hn-serve-refuses-to-touch-authorized_keys).
When a check fails, the command writes nothing, exits with status 1 and names
the path:

```text
hn: hn serve state defect: /home/hn-serve/.ssh: directory mode 0777 is writable by group or others; run chmod 700 /home/hn-serve/.ssh
```

The read-only commands `repo list`, `repo show` and `key list` refuse in the
same way. `hn serve repo lock-exec` checks before it starts its command, so a
refused `lock-exec` runs nothing. Fix the path and rerun the command; it
rewrites the block.

A registry binding whose stored public key does not parse, or does not match
its fingerprint, also keeps the block from being written. This can happen
after a hand edit of `state/registry.json`. In that case `repo create`,
`repo set` and `key add` refuse. `repo list`, `repo show`, `key list` and
`repo lock-exec` print
`hn serve: warning: authorized_keys was left unchanged because ...`, which
names the fingerprint, and then run, so you can find the binding. Remove it
with `hn serve key remove FINGERPRINT`, which also rewrites the block. The old
block stays safe in the meantime: each entry's forced command names only a
fingerprint, and `hn serve git` looks the actor up in the registry when the
key connects.

### Running a command under the repository lock

`hn serve repo lock-exec NAME -- COMMAND [ARG]...` runs one command in the bare
repository while it holds the repository lock, for repairs outside the
governed push path. The procedure for a protected branch whose tip has no
valid policy is in
[Recovering a protected branch](#recovering-a-protected-branch).

## Connecting over SSH

Clients reach a hosted repository through the server account's OpenSSH
login. Each key in the managed `authorized_keys` block runs
`hn serve git --key FINGERPRINT` as a forced command, so a connection can only
fetch from a hosted repository, push to it, or transfer its Git LFS objects.

### OpenSSH settings on the server

The server needs an OpenSSH daemon that allows public-key login for the server
account. Two daemon defaults matter:

- `StrictModes yes` makes `sshd` ignore `authorized_keys` when the home
  directory, `~/.ssh` or the file itself is writable by group or others. Keep
  the home directory at mode 0755 or stricter. `hn serve` creates `~/.ssh` with
  mode 0700 and `authorized_keys` with mode 0600, and refuses to write either
  one when its mode is unsafe.
- `PermitUserEnvironment no` stops a client from setting environment
  variables through `~/.ssh/environment` or `environment=` options. Keep it.
  `hn serve git` rebuilds Git's environment in any case, as described in
  [How a session runs](#how-a-session-runs).

Git protocol version 2 needs `AcceptEnv GIT_PROTOCOL` in `sshd_config`,
because the client sends its protocol request in that variable. Without it,
clients fall back to protocol version 0, which works the same way for every
command on this server.

The server account needs Git 2.11 or later on its `PATH`. Git 2.10 added push
options and Git 2.11 added object quarantine for `pre-receive` hooks, and the
push checks depend on both (see the
[2.10.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.10.0.adoc)
and

### Clone URLs

`hn serve repo create` prints the clone URL of a new repository. Both URL forms
Git supports for SSH work:

```text
git clone ssh://hn@server.example/demo.git
git clone hn@server.example:demo.git
```

Here `hn` is the server account and `demo` the hosted repository name. The path
is the repository name, with or without a leading `/` and with or without the
`.git` suffix. It never has more than one segment, so `ssh://hn@server/demo`
and `hn@server:/demo.git` name the same repository, while `hn@server:a/demo.git`
and `ssh://hn@server/~/demo.git` are refused. A non-default port goes in the
URL as usual, for example `ssh://hn@server.example:2222/demo.git`.

### Requests the server accepts

| Client command | SSH request | What the server does |
|----|----|----|
| `git clone`, `git fetch`, `git pull`, `git ls-remote` | `git-upload-pack 'demo.git'` | Runs `git upload-pack --strict` on the hosted repository |
| `git push` | `git-receive-pack 'demo.git'` | Takes the repository lock and runs `git receive-pack` with the server's hooks |
| `git lfs` transfers | `git-lfs-transfer 'demo.git' upload` or `download` | Serves the repository's LFS objects, as described in [Large files with Git LFS](#large-files-with-git-lfs) |

The server also accepts the older spellings `git upload-pack` and
`git receive-pack`. It refuses every other request, including interactive
shells, `scp`, `sftp`, `git archive --remote` (`git-upload-archive`) and
`git-lfs-authenticate`. The `restrict` option on each managed entry also
disables port, agent and X11 forwarding and terminal allocation.

### How a session runs

When a key connects, `hn serve git` checks the layout read-only, looks the
fingerprint up in the registry and parses the request. It parses the request
byte by byte against a fixed grammar and never passes it to a shell. It then
starts Git directly with an environment built from scratch: `PATH`, `HOME`,
`LANG=C`, `GIT_CONFIG_NOSYSTEM=1`, `TMPDIR=$HOME/.hn-serve/state/tmp`,
`GIT_PROTOCOL` when the client sent exactly `version=N`, and the mapped actor,
key and repository in `HN_SERVE_ACTOR`, `HN_SERVE_KEY` and
`HN_SERVE_REPOSITORY`. A push runs with `core.hooksPath`,
`receive.fsckObjects` and `receive.advertisePushOptions` given on Git's command
line, which take precedence over anything in the hosted repository's `config`.
The `pre-receive` hook then decides which ref updates to accept, as described
in [Push verdicts and ref classes](#push-verdicts-and-ref-classes).

Fetches never take the repository lock and never wait for a push. Pushes to one
repository run one at a time: a push holds the repository lock from before Git
starts until `receive-pack` exits. A push that cannot get the lock within 120
seconds is refused with `repository-busy`. Pushes to different repositories do
not wait for each other.

### Refusals

A refused session prints one `hn-serve/1` rejection line with `ref=-` and one
sentence to stderr, then exits with status 1 before Git starts. Nothing in any
hosted repository changes. Git shows the two lines and then its own error:

```text
hn-serve/1 reject ref=- actor=- code=unknown-key next="ask the administrator to run hn serve key add"
hn-serve: this SSH key is not registered with the server.
fatal: Could not read from remote repository.

Please make sure you have the correct access rights
and the repository exists.
```

The checks run in this order, and the first failure decides the code:

| Code | Cause | What to do |
|----|----|----|
| `unknown-key` | The key's fingerprint is not in the registry, for example after `hn serve key remove` | Ask the administrator to bind the key with `hn serve key add` |
| `unsupported-command` | The request is not one of the accepted requests, has extra arguments, quotes or shell characters, or names a path with more than one segment | Use `git fetch`, `git push` or `git lfs` with a clone URL of the form above |
| `unhosted-repository` | No hosted repository has that name | Check the name with the administrator, who can run `hn serve repo list` |
| `repository-busy` | Another push held the repository lock for more than 120 seconds | Retry the push |

A key that is not in the managed block at all never reaches `hn serve`;
`sshd` refuses it with `Permission denied (publickey).`. The `actor` field
names the mapped actor for every code except `unknown-key`. The full line
format and the table of every reason code are in
[protocol-v0.md](protocol-v0.md#rejection-lines).

When the server layout itself is unsafe, for example a hosted repository
directory replaced by a symbolic link, every session stops before any key or
request check with an `hn: hn serve state defect: PATH: REASON` line. The
administrator fixes it as described in
[What makes the server refuse to run](#what-makes-the-server-refuse-to-run).

## Push verdicts and ref classes

Every push runs the server's `pre-receive` hook, `hn serve hook pre-receive`,
inside `git receive-pack`. The hook decides the push verdict while
`hn serve git` holds the repository lock, so no other push can move a ref in
between. The hook itself never takes the lock.

### One verdict for the whole push

The hook accepts a push only when every ref update in it passes. When any ref
update fails, the hook prints one rejection line pair for each failing ref
update and exits with status 1. Git then rejects every ref update in the push,
including the ones that passed, and nothing in the hosted repository changes.

Git keeps the objects of a push in a quarantine directory until the
`pre-receive` hook accepts it (Git 2.11 or later). The hook can read every pushed
object there, while fetches and other pushes cannot see them. When the hook
rejects the push, Git deletes the quarantine directory, so the rejected commits
never enter the hosted object database.

Use `git push --atomic` when you push several refs. The server treats a push
with or without `--atomic` the same way, but with `--atomic` Git's own summary
also reports every ref as rejected together.

### Ref classes

The hook puts each ref update into exactly one class, checking the classes in
this order:

| Class | Ref pattern |
|----|----|
| `protected` | a branch listed as protected in the repository configuration |
| `actor` | `refs/hn/actors/` followed by 64 lowercase hex digits |
| `proposal` | `refs/hn/proposals/` followed by 64 lowercase hex digits |
| `memory` | `refs/hn/memory/ACTOR/STREAM`, each part 64 lowercase hex digits |
| `tag` | `refs/tags/NAME` |
| `branch` | any other `refs/heads/NAME` that `git check-ref-format` accepts |
| `reserved` | everything else |

Git itself refuses ref names that `git check-ref-format` rejects before the
hook runs, so every `refs/heads/` name Git lets through is an ordinary branch.
That includes names Git accepts in a full ref but not as a short branch name,
such as `refs/heads/@`.

The rules for the `actor`, `proposal` and `memory` classes are in
[Hubnot fact refs and budgets](#hubnot-fact-refs-and-budgets). The rules for
protected branches are in [Protected branches](#protected-branches).

The hook checks the classes in a fixed order: actor refs first, then memory
refs, then proposal refs, then tags, ordinary branches and reserved refs, and
protected branches last. A later class may rely on facts that an earlier class
of the same push brought along. For example, one push can carry a new proposal
event in an actor ref together with the proposal's code ref.

### Ordinary branches and their owners

Any mapped actor may create an ordinary branch and may fast-forward it. A
forced update, where the old tip is not an ancestor of the new one, and a
deletion are accepted only from the branch's owner or from a maintainer of the
repository. Anyone else gets `branch-not-owner`.

The owner of a branch is the actor whose push created it. The `post-receive`
hook records the owner in `state/repos/NAME/branches.json` after the push
succeeds and removes the record when the branch is deleted. A forced update
keeps the record unchanged. Protected branches never get owner records.

A branch without a record has no owner. That covers the branches imported by
`hn serve repo create` and any branch whose record could not be written. Only
a maintainer may force-update or delete such a branch.

A maintainer of the repository is an actor listed in `maintainers` of the
`.hn/policy.json` file at the tip of the default protected branch, which is
the first protected branch in the configuration. The hook reads that policy
for each push. When the tip has no policy file, or the file is not valid
`hn.policy/0`, no actor counts as a maintainer.

### Tags

Any mapped actor may create a tag. A push that moves or deletes an existing
tag is rejected with `tag-immutable`. Create a new tag instead.

### Reserved refs

A ref outside every class above is rejected with `reserved-ref`. That includes
the server marker `refs/hn/serve/v1`, every other `refs/hn/serve/` ref, notes
in `refs/notes/`, remote-tracking refs, and `refs/hn/` names that do not match
the patterns in the class table, such as `refs/hn/actors/` followed by
anything other than a full actor fingerprint.

### Push options

The server accepts three push options, each at most once:

| Option | Value |
|----|----|
| `hn-advance` | a full candidate event ID, `sha256:` followed by 64 lowercase hex digits |
| `hn-expected-tip` | a full commit ID |
| `hn-rule` | an automerge rule name, 1 to 64 of `A-Z a-z 0-9 - _ .`, excluding `.` and `..` |

A push with any other option, a repeated option or a malformed value is
rejected: every ref update in it gets `unsupported-command` with the sentence
`push options other than hn-advance, hn-expected-tip and hn-rule are not supported.`.
`hn-rule` without `hn-advance` in the same push is rejected the same way.
A push with `hn-advance` must contain exactly one ref update, to a protected
branch; otherwise every ref update gets `unsupported-command` as well.
[Advancing a protected branch](#advancing-a-protected-branch) describes what
`hn-advance` and `hn-expected-tip` do, and
[Automerge rules](#automerge-rules) describes `hn-rule`.

### Ref update limits

The hook accepts at most 10,000 ref updates and 4 MiB of ref update lines in
one push. A larger push is rejected as a whole, and every ref update in it
gets its own `over-budget` line pair with `budget=ref-updates`, in ref order
like any other rejection. When the push has more than 10,000 ref updates,
`limit=10000` and `measured` is the number of ref updates. When the lines take
more than 4 MiB, `limit=4194304` and `measured` is their size in bytes; the
sentence says which limit applies. The push log entry lists every ref update
with one `over-budget` code each. Split such a push into several smaller
pushes.

The hook keeps memory use bounded for any number of ref updates. Past either
limit it writes the ref updates to a private scratch directory in
`state/tmp/` to sort them, and removes the directory before it exits.

### Rejection lines

Each rejected ref update produces one `hn-serve/1` rejection line and one
sentence. The line names the ref, the mapped actor that pushed, a reason code,
the IDs involved and the next action. Git relays both lines with a `remote: `
prefix, in byte order of the ref names, before its own summary. The line
format and the full table of reason codes are in
[protocol-v0.md](protocol-v0.md#rejection-lines).

<!-- example: reject-branch-not-owner -->
Actor `4f1c9a6d` force-pushes `feature/b`, which actor `8a4b76e4` created (US1-6):

```text
remote: hn-serve/1 reject ref=refs/heads/feature/b actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=branch-not-owner ids=8a4b76e4bcacb0871f481b895d3be3de30d633f0fec3117a1d76485bc46d4e23 next="ask the owner or a maintainer"
remote: hn-serve: refs/heads/feature/b belongs to 8a4b76e4bcacb0871f481b895d3be3de30d633f0fec3117a1d76485bc46d4e23; only its owner or a maintainer can force-update or delete it.
```

For an ordinary branch without an owner record the line has no `ids` field
and the sentence says the branch has no recorded owner. A moved tag lists its
old and new commit IDs in `ids`, and a deleted tag lists its old commit ID.

When the hook cannot trust the session it refuses before it reads any ref
update and prints one line of the form `hn: hn serve hook: REASON`. That
happens when the hook runs outside `hn serve git`, when `GIT_DIR` is not the
hosted repository, or when the pushing key was removed or bound to another
actor while the push was running. Git rejects the whole push.

### The push log

The server appends one JSON line per push to `state/repos/NAME/push.log`. The
`pre-receive` hook writes the entry for a rejected push and the
`post-receive` hook writes the entry for an accepted push. Each entry has
these fields:

| Field | Content |
|----|----|
| `time` | RFC 3339 UTC time of the verdict |
| `actor` | the mapped actor that pushed |
| `key` | the fingerprint of the key that authenticated |
| `verdict` | `accepted` or `rejected` |
| `updates` | each ref update as `ref`, `old` and `new` commit IDs, with all zeros for a creation or a deletion |
| `codes` | the reason codes in the order of the rejection lines; empty for an accepted push |

The server never reads the log back, and the verdict never depends on it. A
log that reaches 64 MiB stops every session with a state defect, so the
server refuses an append that would cross that size and reports it instead.
Rotate the log before it gets there by moving it out of the state directory
under the repository lock, for example with
`hn serve repo lock-exec NAME -- mv /home/hn/.hn-serve/state/repos/NAME/push.log /var/log/hn-serve/NAME-push.log`,
where `/home/hn` is the server account's home directory. The next push starts
a new log.

The `post-receive` hook never changes the verdict. If it cannot record an
owner or append to the log, it prints a line starting with
`hn-serve: post-receive bookkeeping failed:` and Git still reports the push as
successful. A branch whose owner record is missing then behaves as a branch
without an owner.

## Hubnot fact refs and budgets

Three ref classes carry Hubnot facts: actor chains in `refs/hn/actors/ACTOR`,
proposal code refs in `refs/hn/proposals/ID` and memory streams in
`refs/hn/memory/ACTOR/STREAM`. The `pre-receive` hook checks them with the same
validation code `hn sync` uses when it imports facts from a remote, so the
server accepts a fact ref exactly when a client would import it. `hn sync`
publishes each of these refs in its own `git push`, so one sync can produce
several push log entries.

### Who may push each fact ref

| Ref | Who may push it | What the push may do |
|----|----|----|
| `refs/hn/actors/ACTOR` | only the actor bound to the pushing key | create the chain, then append events |
| `refs/hn/proposals/ID` | any mapped actor | create the ref once, at the candidate's signed head |
| `refs/hn/memory/ACTOR/STREAM` | only the actor bound to the pushing key | create the stream, then append memories |

The actor comes from the key binding that `hn serve key add` made. Nothing in
the pushed data can change it. `hn sync` publishes the refs under
`refs/hn/actors/`, `refs/hn/proposals/` and `refs/hn/memory/`. The chains it
imports from a remote live under `refs/hn/remotes/`, which it never publishes,
so an ordinary sync pushes only the clone's own chain.

### Actor chains are append-only

Signed history is immutable: a correction is a new signed event that refers
to the earlier one. The server therefore refuses a push that deletes an
actor chain or moves it to a commit that does not descend from the hosted
value, with `actor-chain-rewrite`. That includes a forced push of an earlier
commit and a diverging chain whose new event reuses a sequence number the
hosted chain already has. Append new events instead.

The checks for an actor chain run in this order, and the first failure is
reported:

1. A deletion or a non-descending update is `actor-chain-rewrite`.
2. A chain of another actor is `actor-key-mismatch`.
3. The push must fit the repository budgets, and the hosted facts with the
   push must stay within the hosted fact ceilings, otherwise `over-budget`.
4. Each appended event must carry a valid signature by the chain's actor,
   continue the sequence and the previous event ID, have the previous
   event's commit as its only parent, and hold exactly `event.json`,
   `signature` and the typed attachments of its kind: `log.txt` for a run
   result, `audit.pack` for an audit fact and both for an audit result, as
   described under [Audit facts](#audit-facts). A failure is
   `actor-chain-invalid` and names the full event ID of the first failing
   event, computed from its `event.json` even when the signature is broken,
   or its commit when `event.json` cannot be read. When the signature
   verifies and an attachment does not, the sentence quotes the failed
   attachment check.
5. Every fact an appended event refers to, such as the issue a comment
   answers, the proposal a review or run request names, decision evidence or
   an identity authorization, must be hosted or arrive earlier in the same
   push. A missing one is `dependency-missing` and names its full ID. A
   reference to the wrong kind of event, or a decision or merge that does not
   match its proposal, is `actor-chain-invalid`.
6. The hosted facts plus the push must still form a valid projection: exact
   event references, issue relationships and identity continuity. A failure
   is `actor-chain-invalid`.

The server reads the hosted facts once per push and validates only the
events the push appends, so the cost of a push grows with what it adds.
The one exception is hosted audit facts: the read verifies every hosted
`audit.pack` again, so verdict time also grows with the bytes of the hosted
audit packs. The number of Git processes the read starts does not grow with
the number of audit facts. The exact membership, closure and shape checks
read the objects the pack parser decoded, identical packs are checked once,
and Git's object syntax check indexes the hosted packs together in one
temporary repository, with one `git index-pack` per 64 MiB of packs. The read
holds the decoded commits and trees of one pack at a time: once a pack is
checked against every fact that carries it, only its object IDs and its
entries in the stored pack are kept. The bytes the packs expand to are
bounded by the `hosted-audit-expanded-bytes` ceiling under
[Hosted fact ceilings](#hosted-fact-ceilings).

The server's acceptance is never evidence. A client that fetches from this
server validates every fact again before it uses it, and a signed fact is
trusted only through the policy at the relevant commit. A server that
accepted a forged fact would still not make clients trust it.

### Audit facts

[Native observational audits](audits-v1.md) are events in the signer's
actor chain, so they reach the server in an ordinary actor push and pass the
checks above. Each audit event also holds `audit.pack`, the inert snapshot
pack described under
[Snapshot dependency transport and admission](audits-v1.md#snapshot-dependency-transport-and-admission),
and an `audit.result` holds its `log.txt` as well. The server checks them
with the code `hn sync` uses when it imports the same chain:

- The server parses `audit.pack` and hashes each object before Git reads it.
  It compares the pack's objects with the exact set the signed fact names,
  computed from the pack's own objects as a repository holding only the pack
  would answer, and checks their syntax with `git index-pack --fsck-objects`
  in a private temporary repository. Git sets `GIT_QUARANTINE_PATH`, `GIT_OBJECT_DIRECTORY` and
  `GIT_ALTERNATE_OBJECT_DIRECTORIES` for the `pre-receive` hook. The server
  removes them, and the other variables that point Git at another repository
  or object store, for every command in the temporary repository, so hosted
  objects cannot supply an object the pack omits. Those commands also read
  no system, global or environment configuration, whatever the server's
  environment enables or excludes, and the temporary repository is created
  without a template, so no `init.templateDir` or `GIT_TEMPLATE_DIR` can
  link it to another object database. Verification writes only inside the
  temporary repository and removes it. Only a verified pack is installed,
  and only into the push's quarantine, so a rejected push leaves the hosted
  object database unchanged.
- An audit result's `log.txt` must match the signed `log` digest and stay
  within 1 MiB.
- The rule predecessors, authorization, request and native workflow
  revision an audit event names must be hosted or arrive earlier in the same
  push, otherwise `dependency-missing`.
- The signer must hold the audit role in the policy at the event's recorded
  policy commit, which travels in the pack. This is historical validity. The
  hosted branches need no `audits` section, and the server never reads or
  sets a private audit authority selection, so an accepted audit fact gives
  nobody current authority to request or execute audits.

Audit attachments count toward the budgets and the hosted fact ceilings as
described under [Budgets](#budgets) and
[Hosted fact ceilings](#hosted-fact-ceilings).

Audits are observational on protected branches. A protected update never
counts an audit fact as a review, CI result, decision or merge evidence. A
failed audit of a ready candidate's head does not block the update, and a
passing audit does not supply a missing CI result, even when the audit rule
runs the protected pipeline's own definition and its executor is a trusted
runner.

### Proposal code refs and the code-ref exception

A proposal code ref names the commit a proposal event signs as its head.
`hn proposal open` and `hn proposal revise` create it beside the event.
The server accepts a new `refs/hn/proposals/ID` when:

1. it does not exist yet; moving or deleting a hosted proposal ref is
   `proposal-ref-immutable`,
2. the candidate event `sha256:ID` is hosted or arrives in an actor ref of
   the same push, otherwise `dependency-missing`,
3. the candidate is a proposal event whose signed head is the pushed
   commit, otherwise `proposal-ref-mismatch` naming the candidate, its signed
   head and the pushed commit,
4. the pushed commit descends from the candidate's signed base, otherwise
   `proposal-ref-mismatch`,
5. the candidate's code fits the repository budgets, otherwise
   `over-budget`.

To change the code of a proposal, create a revision with
`hn proposal revise`. The revision is a new candidate with its own code ref,
and both histories stay available.

Candidate code may arrive after the candidate. An actor chain whose
`proposal.open` or `proposal.revise` event has no hosted code ref, and no
code ref in the same push, is accepted when the proposal's base commit is
hosted or in the push and, whenever the head commit is present, the head
descends from the base. This lets `hn sync` push the actor chain and then the
code ref in separate pushes, and lets one push carry both. The exception
cannot advance a protected branch: an advancement requires the candidate's
hosted code ref to equal the commit being pushed, as described in
[Protected branches](#protected-branches).

### Memory streams

A memory stream holds one actor's `hn-memory/0` memories. The server accepts
an update of `refs/hn/memory/ACTOR/STREAM` when it creates the stream or
appends to it, the actor is the one bound to the pushing key, the push fits
the budgets, and the whole stream at the pushed commit passes the same
`hn-memory/0` validation `hn sync` applies on import: every memory is signed
by the stream's owner and continues the stream's sequence and previous
memory ID. A deletion, a rewrite or a validation failure is `memory-invalid`,
and a stream of another actor is `memory-key-mismatch`.

### Budgets

Each repository has five push budgets. `hn serve repo create` sets the same
defaults `hn replication select` uses, `hn serve repo show NAME` prints them,
and `hn serve repo set NAME` changes them (see
[Changing protected branches, quotas and budgets](#changing-protected-branches-quotas-and-budgets)):

| Budget | Default | What is measured for one pushed ref |
|----|----|----|
| `max-events` | 10000 | events in the whole actor chain or memory stream after the push, hosted ones included |
| `max-objects` | 100000 | Git objects the push makes reachable from the ref that the hosted value did not already reach, plus the snapshot objects its audit packs expand to |
| `max-object-bytes` | 67108864 (64 MiB) | the largest of those objects, expanded snapshot objects included |
| `max-attachment-bytes` | 16777216 (16 MiB) | the largest event attachment in the chain: a run log, an `audit.pack` or an audit result log |
| `max-total-bytes` | 1073741824 (1 GiB) | the total size of those objects, expanded snapshot objects included |

Limits are inclusive: a measurement equal to its limit passes, and one above
it is rejected with `over-budget`. The rejection line names the first budget
the push exceeds, in the order of the table, with its limit and the
measurement, for example
`budget=max-events limit=11 measured=12`. When a push exceeds several budgets
at once, the server still measures every byte budget before it chooses, so a
push over both `max-object-bytes` and `max-total-bytes` is reported as
`max-object-bytes`, with the size of the largest object as the measurement.
The hosted refs stay unchanged.

An object the hosted value of the ref already reaches is not counted again,
whatever file it was before. A run log with the same bytes as an earlier
event's `event.json`, signature blob or run log adds no object and no bytes.
For an actor ref the server counts the same objects and bytes that client
replication counts for the same chain, so a push measured at exactly a limit
on the client is accepted.

An `audit.pack` counts twice. As an attachment and as a Git object of the
chain it counts at its stored, compressed size. The objects it expands to
count as well, at their expanded sizes, before the server unpacks anything:
a 1 MiB file that compresses into a 2 KB pack counts as a 1 MiB object. An
expanded object that an `audit.pack` of the hosted chain already holds is not
counted again, and one that several packs of the same push hold counts once.

A proposal code ref is new when it is pushed, so its measurement covers every
object reachable from the proposal's head, including the history it shares
with hosted branches, the way client replication measures a new proposal
selection. Repositories with long histories may need a higher
`max-objects` or `max-total-bytes` before their proposal refs fit.

### Hosted fact ceilings

Every push that updates a fact ref or a protected branch reads all hosted
actor chains into memory to check the push against them. Three ceilings bound
that read for the whole repository. They are fixed in this build and are
the same aggregate limits `hn` uses when it reads issue history in a clone:

| Ceiling | Value | What is counted |
|----|----|----|
| `hosted-fact-events` | 100000 | events in all hosted actor chains together |
| `hosted-fact-bytes` | 268435456 (256 MiB) | bytes of every hosted event's `event.json`, `signature` and attachments together: run logs, audit packs and audit result logs |
| `hosted-audit-expanded-bytes` | 1073741824 (1 GiB) | bytes the objects of every hosted audit event's `audit.pack` expand to, each event's pack counted in full even when another event carries the same pack |

A single object may use the whole byte ceiling, so any event and attachment
the five budgets admit can be read back, whatever the budgets were when it
was admitted. A run log of up to 16 MiB is accepted with the default budgets and
stays readable on every later push.

The server checks the ceilings before it accepts an actor chain. A push that
would bring the hosted facts above any ceiling is rejected with
`over-budget`, `budget=hosted-fact-events`, `budget=hosted-fact-bytes` or
`budget=hosted-audit-expanded-bytes`, the ceiling as `limit` and the total the
hosted facts would reach as `measured`. Like the budgets, the ceilings are
inclusive, and they are checked in the order of the table. The check runs
after the five budgets. Because of it, an accepted push can never make the
hosted facts unreadable for the next push.
The ceilings do not apply to proposal code refs and memory streams, which
the hosted fact read does not load.

A repository that reaches a ceiling accepts no further actor events. Other
refs, including ordinary branches, tags, proposal code refs and memory
streams, are still checked as usual. Signed history cannot be removed, so
start a new hosted repository for further collaboration when a repository
approaches 256 MiB of facts or 1 GiB of expanded audit snapshots.
`hn serve repo show` does not print the ceilings because they cannot be
changed.

If the hosted facts cannot be read for any other reason, for example damaged
objects, the server refuses every fact ref and protected update as described
under [Rejection codes for fact refs](#rejection-codes-for-fact-refs).

### Identity rotation

The server binds each key to one actor. After `hn identity rotate`, a clone
still holds the predecessor's chain under `refs/hn/actors/`, and `hn sync`
from that clone with the successor's key gets `actor-key-mismatch` for the
predecessor's chain. `hn sync` stops publishing at the first rejected push,
so the refs it would have pushed after that chain stay unpublished too. Bind
a key for each actor with `hn serve key add` and push each chain with its own
actor's key.

### Rejection codes for fact refs

| Code | Cause |
|----|----|
| `actor-chain-rewrite` | the push deletes or rewrites a hosted actor chain |
| `actor-key-mismatch` | the actor chain belongs to another actor |
| `actor-chain-invalid` | an appended event fails signature, sequence, shape or relationship validation, or the hosted facts could not be read |
| `dependency-missing` | a referenced event, candidate or commit is not hosted and not in the push |
| `proposal-ref-immutable` | the push moves or deletes a hosted proposal code ref |
| `proposal-ref-mismatch` | a new proposal code ref is not the candidate's signed head or does not descend from its base |
| `memory-key-mismatch` | the memory stream belongs to another actor |
| `memory-invalid` | the push deletes or rewrites a memory stream, or the stream fails `hn-memory/0` validation |
| `over-budget` | the pushed ref exceeds one of the budgets, or an actor chain would take the hosted facts past a hosted fact ceiling |

When the server cannot read its hosted facts, every fact ref and every
protected branch update in the push is rejected with `actor-chain-invalid`
and the sentence `hn-serve: hosted facts could not be verified; ask the administrator.`.
The other refs of the push are still checked. The next action for each code
is in [protocol-v0.md](protocol-v0.md#rejection-lines).

Actor `4f1c9a6d` fetches actor `8a4b76e4`'s chain from that actor's clone and
pushes it (US1-3):

```text
remote: hn-serve/1 reject ref=refs/hn/actors/8a4b76e4bcacb0871f481b895d3be3de30d633f0fec3117a1d76485bc46d4e23 actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=actor-key-mismatch next="push only refs/hn/actors/4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c"
remote: hn-serve: refs/hn/actors/8a4b76e4bcacb0871f481b895d3be3de30d633f0fec3117a1d76485bc46d4e23 belongs to actor 8a4b76e4bcacb0871f481b895d3be3de30d633f0fec3117a1d76485bc46d4e23 and this key is bound to actor 4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c.
```

## Protected branches

A protected branch moves only when the commit it moves to is the signed head
of a proposal that the repository's governance has accepted and tested.

### What protects a branch

The server configuration decides which branches are protected. The list lives
in `state/repos/NAME/config.json`, defaults to `refs/heads/main`, and changes
only through `hn serve repo create --protect` and `hn serve repo set`, as
described in
[Changing protected branches, quotas and budgets](#changing-protected-branches-quotas-and-budgets).
The server never reads this list from pushed content, so a push cannot
unprotect a branch.

### The protected branch invariant

After every successful push, the tip of each protected branch is the signed
head of a candidate that is ready and accepted under two policies: its signed
base policy, and the destination policy, which is the `.hn/policy.json` at the
tip the push replaced. That head carries the trusted CI results both policies
require. The server checks this with the same signed facts every client can
verify. It never creates a commit and never signs anything, and its
acceptance is not evidence: a client trusts the branch only through the facts.
When an advancement request names an automerge rule, the rule's standing
acceptance takes the place of maintainer acceptance, and the base policy and
the destination policy must be the same policy, as
[Automerge rules](#automerge-rules) describes.

### The checks for a protected update

For each update of a protected branch from the current tip `T` to the pushed
commit `H`, the server runs these checks in order and reports the first one
that fails:

1. A deletion is `protected-deletion`.
2. A creation is `protected-policy-invalid`. Only the administrator creates a
   protected branch, with `hn serve repo create` or `hn serve repo set`.
3. With `hn-expected-tip`, a tip other than `T` is `protected-stale-tip`. This
   check comes before every policy and candidate check, so the loser of a
   race always gets this code.
4. A tip `T` without a valid `.hn/policy.json` is `protected-policy-invalid`.
   Every update of the branch is refused until the administrator repairs it,
   as described in [Recovering a protected branch](#recovering-a-protected-branch).
5. A head `H` that does not descend from `T` is `protected-not-fast-forward`,
   naming `T` and `H`.
6. When no candidate in the hosted facts or the push has `H` as its signed
   head, the update is `protected-no-proposal` with
   `missing=proposal,review,ci,acceptance`. With `hn-advance`, the named
   candidate is the only one considered, and it must have head `H`.
7. A candidate whose base commit has no valid `.hn/policy.json` is
   `protected-policy-invalid`.
8. The candidate's code ref `refs/hn/proposals/ID` must be hosted or arrive in
   the same push and point at `H`; otherwise the update is
   `proposal-ref-mismatch` with `missing=proposal`.
9. A candidate that a revision superseded, whose lineage another merged
   candidate closed, whose lineage has competing merges, that is already
   recorded as merged, or that a maintainer currently rejects under its base
   policy is `protected-blocked`. The line names the blocking events.
10. A candidate that is not ready or not accepted under its base policy is
    `protected-not-ready`, with `missing` naming each unmet kind: `review`,
    `ci` or `acceptance`.
11. A candidate that is not ready or not accepted under the destination
    policy is `protected-destination-policy`, with the unmet kinds and a
    sentence naming each unmet threshold.
12. When the destination opts in to
    [protected checks](governance-v0.md), the candidate must have been
    evaluated under that same policy, and no protected path may have changed
    between the candidate's base and `T`. Otherwise the update is
    `protected-destination-policy` with `missing=proposal` and next step
    `revise ID against T`. This is the guard `hn merge` applies before a local
    merge, so a stale candidate cannot carry its approvals past a newer
    protected baseline.
13. With `hn-advance`, a pushing actor who is not a maintainer under both the
    base and the destination policy gets `advance-not-maintainer`.

An advancement request that names an automerge rule with `hn-rule` adds step
7a, judges steps 10 and 13 by the rule and skips step 11, as
[Automerge rules](#automerge-rules) describes.

Facts in the same push count once their actor refs have passed. A maintainer
can push an acceptance in `refs/hn/actors/ACTOR` together with the protected
update, and the update is checked with that acceptance. Code counts when its
proposal ref is hosted or arrives in the same push, so the code-ref exception
for actor chains described in
[Proposal code refs and the code-ref exception](#proposal-code-refs-and-the-code-ref-exception)
never lets a branch move to code the server does not hold.

### Base policy and destination policy

With protected checks enabled, a candidate that changes a protected path is
not ready in steps 10 and 11 until it has the required approvals from
protected-check reviewers, and the rejection sentence names the changed
paths.

Steps 10 and 11 evaluate the same signed reviews, CI results and decisions
twice. Step 10 uses the policy at the candidate's base commit, the policy the
maintainers signed their decisions against. Step 11 uses the destination
policy's maintainers, trusted reviewers, trusted runners, pipelines and
thresholds, while it still matches decisions by the base policy digest. A
reviewer that the destination policy no longer trusts adds nothing to step 11,
and a pipeline that only the destination policy requires must have a valid
definition at `H`, or step 11 fails with `missing=ci`. The rules are in
[Destination policy on a protected branch](governance-v0.md#destination-policy-on-a-protected-branch).

For example, when the base policy requires one approval and the destination
policy requires two, a candidate with one approval passes step 10 and fails
step 11 with the sentence part
`destination policy requires 2 approvals; 1 trusted approval found`.

### Fast-forward only, and how to revise a stale proposal

The server never merges, rebases or creates a commit, because the commit that
reaches a protected branch must be the exact commit that CI tested. When the
branch moved after a proposal was opened, so that its head no longer descends
from the tip, the update is `protected-not-fast-forward` and the next action
is `revise the proposal onto T with hn proposal revise`. A revision is a new
candidate with a new head on the current tip, and it needs fresh review, CI
and acceptance.

### Several candidates with the same head

Several candidates may sign the same head, for example a rejected proposal
and a later proposal for the same commit. Without `hn-advance`, the update is
accepted when any of them passes steps 7 to 11. When none passes, the line
reports the candidate whose first failing check comes latest in the list,
choosing the lowest event ID when two fail at the same check, and `ids` lists
every candidate with head `H` before any other ID.

### Who may push a protected branch

Any mapped actor may push a protected branch directly with `git push`, and the
push passes under the same checks. Such a push does not need to come from a
maintainer, because the signed facts already carry the maintainers'
acceptance. An advancement request with the `hn-advance` push option, which
`hn merge --remote` sends, additionally requires the pushing actor to be a
maintainer under both policies (step 13). See
[Advancing a protected branch](#advancing-a-protected-branch). A request that
also names an automerge rule with `hn-rule` requires the pushing actor to be
one of the rule's executing actors instead, as
[Automerge rules](#automerge-rules) describes.

### Rejection examples for protected branches

<!-- example: reject-direct-main -->
A mapped actor pushes `main` one commit ahead with no proposal (US1-2):

```text
remote: hn-serve/1 reject ref=refs/heads/main actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=protected-no-proposal ids=9b2e4c6a8d0f1e3c5a7b9d1f3e5c7a9b2d4f6e8a missing=proposal,review,ci,acceptance next="open a proposal for 9b2e4c6a8d0f1e3c5a7b9d1f3e5c7a9b2d4f6e8a"
remote: hn-serve: refs/heads/main is protected and 9b2e4c6a has no accepted, CI-tested proposal.
```

A candidate with an approval and no CI result or acceptance gets
`code=protected-not-ready`, `ids` naming the candidate,
`missing=ci,acceptance` and `next="run hn proposal status ID"`. Run that
command to see which evidence is missing.

## Recovering a protected branch

When the tip of a protected branch has no valid `.hn/policy.json`, every
update of that branch is refused with `protected-policy-invalid`, because
there is no destination policy to check it against. Governed pushes cannot
repair the branch. The administrator repairs it outside the governed push
path:

1. Prepare a repaired commit that descends from the current tip and restores
   a valid `.hn/policy.json`. Review it with the maintainers out of band, for
   example with `hn policy check`, since no hosted governance can approve it.
2. Push the repaired commit to an ordinary branch of the hosted repository,
   or fetch it into the bare repository, so the server holds its objects.
3. Move the branch under the repository lock, naming both the repaired
   commit and the current tip:

   ```sh
   sudo -u hn-serve hn serve repo lock-exec pingpong -- git update-ref refs/heads/main REPAIRED CURRENT
   ```

`git update-ref` with an old value moves the branch only when it still points
at `CURRENT`. If a push or another administrator moved it in the meantime,
the command fails and changes nothing, so check the new tip and start again.

This procedure bypasses governance by design. The server signs nothing and
keeps no record of it apart from its effect on the branch, so record the
repair, the commit and the reason in the administrator's own records. After
the repair, protected updates are checked against the restored policy again.

## Advancing a protected branch

A maintainer moves a protected branch to the head of an accepted proposal
with one command, run in any clone that has the maintainer's identity and the
proposal's evidence:

```text
hn merge PROPOSAL --remote REMOTE [--branch BRANCH]
```

`PROPOSAL` is the full candidate event ID. `REMOTE` is the name of a Git
remote that points at an `hn serve` repository. `BRANCH` defaults to `main`
and may be a short name or a `refs/heads/` ref. The maintainer needs no push
rights to the branch: the server moves it only when the signed facts allow
it, and the maintainer's client signs the merge fact afterwards. The server
signs nothing.

### Who may advance a branch

The identity in the clone must be a maintainer under the candidate's base
policy, which the client checks before it contacts the server. The server
also requires the pushing actor to be a maintainer under the destination
policy, the `.hn/policy.json` at the branch tip, and refuses anyone else with
`advance-not-maintainer`. A participant who is not a maintainer can still
push a ready, accepted head to a protected branch with a plain `git push`, as
[Who may push a protected branch](#who-may-push-a-protected-branch)
describes.

### What the command does

The command runs nine steps in order. A failure stops it with exit status 1,
and the message names the step that failed.

1. **Validate locally.** The client runs the checks of `hn merge` that do not
   need a checkout: the full ID, the shallow-clone guards, lineage
   eligibility, no current rejection, enough acceptances, the proposal code
   ref, the maintainer check and readiness under the base policy.
2. **Identify the remote.** The remote must advertise the `refs/hn/serve/v1`
   marker. An ordinary remote is refused with
   `remote REMOTE is not an hn serve remote; use hn merge PROPOSAL in a checkout of the target branch`,
   and nothing is written.
3. **Publish facts.** The client publishes its actor chain, proposal code refs
   and memory streams the way `hn sync` does. A refusal prints the server's
   `hn-serve/1` lines and stops.
4. **Read the tip.** The client reads the branch tip `T` with
   `git ls-remote` and fetches it into `refs/remotes/REMOTE/BRANCH` when the
   commit is not in the clone.
5. **Repair if already advanced.** When the proposal head `H` equals `T` or
   is an ancestor of `T`, the client skips to step 8 without pushing. When
   the clone already holds a merge fact for the candidate, the command prints
   `Proposal ID is already advanced on REMOTE BRANCH and recorded as merged`
   and exits 0.
6. **Request advancement.** The client pushes the head with two push options:

   ```text
   git push --porcelain --push-option=hn-advance=PROPOSAL --push-option=hn-expected-tip=T REMOTE +H:refs/heads/BRANCH
   ```

   On a refusal, the client prints each `hn-serve/1` line and its sentence
   without Git's `remote: ` prefix and exits 1. The branch does not move.
7. **Confirm.** The branch on the server must now be at `H`. Otherwise the
   command exits 1 with
   `server accepted the push but BRANCH is at X; rerun hn merge PROPOSAL --remote REMOTE`.
8. **Record the merge fact.** The client reads its events again, checks that
   the candidate is still accepted, ready, eligible and unmerged and that the
   identity is still a maintainer, then signs `proposal.merged`.
9. **Publish again.** The client publishes the merge fact. If this push
   fails, the fact stays in the clone, and the command exits 1 with
   `merge fact recorded locally; run hn sync REMOTE to publish it`.

The command never creates a commit, never changes the checkout and never
moves a local branch. On success it prints:

<!-- example: advance -->
```sh
hn merge sha256:1c2d3e4f... --remote origin
```

```text
Advanced origin refs/heads/main to 9b2e4c6a8d0f for proposal 1c2d3e4f5a6b
Recorded merge event 7d8e9f0a1b2c with 1 acceptance decision(s)
```

### Why facts travel in their own push

The server evaluates each push as a whole and refuses all of it when any ref
update fails, as
[One verdict for the whole push](#one-verdict-for-the-whole-push) explains.
If the acceptance and the branch update shared one push, a refused
advancement would discard the acceptance too. Step 3 publishes the facts
first, so they stay on the server even when step 6 is refused, and other
participants can see them with `hn sync`.

### The forced refspec and the server's checks

Git refuses a non-fast-forward push on the client unless the refspec starts
with `+`. With that refusal, a maintainer whose proposal no longer descends
from the tip would only see Git's own `non-fast-forward` message. The
command therefore uses `+H:refs/heads/BRANCH`, so Git sends the update and the
server answers with `protected-not-fast-forward`, naming the current tip and
directing `hn proposal revise`. The `+` does not let the push rewrite the
branch: the server's checks in
[The checks for a protected update](#the-checks-for-a-protected-update)
refuse every update that is not a fast-forward to an accepted, tested head.

`hn-advance=PROPOSAL` limits the server to that one candidate.
`hn-expected-tip=T` tells the server which tip the client read in step 4.

### What the merge fact records

The merge fact that step 8 signs has `commit` equal to `head`, because the
branch was fast-forwarded to the exact commit that CI tested. Its `policy` is
the base policy digest, and its `evidence` lists the accepting decisions in
sorted order. Every client validates it like a `--no-ff` merge fact, as
[Fast-forward merge facts](governance-v0.md#fast-forward-merge-facts)
describes.

### Interruptions and reruns

Rerun the same command after any interruption. A rerun checks everything
again and records a missing merge fact exactly once:

| Interrupted after | Server branch | Merge fact in the clone | What a rerun does |
|----|----|----|----|
| Step 3 | unchanged | absent | runs every step |
| Step 6, before the server applied the update | unchanged | absent | runs every step |
| Step 6, after the server applied the update | `H` | absent | takes the step 5 repair path and records the fact once |
| Step 8 | `H` | present, unpublished | publishes the fact in step 3, then reports the branch as already advanced and exits 0 |
| Step 9 | `H` | present, published | reports the branch as already advanced and exits 0 |

The repair path prints:

```text
origin refs/heads/main already contains 9b2e4c6a8d0f for proposal 1c2d3e4f5a6b
Recorded missing merge event 7d8e9f0a1b2c with 1 acceptance decision(s)
```

#### Rerunning a rule advancement

A rule advancement under acceptance mode `rule`, described in
[Automerge rules](#automerge-rules), is also recovered by rerunning the same
command, `hn automerge PROPOSAL --rule NAME --execute --remote REMOTE`. Each
row ends with one rule merge fact for the candidate and one advancement of the
branch:

| Interrupted after | Server branch | Rule merge fact in the clone | What a rerun does |
|----|----|----|----|
| Step 3 | unchanged | absent | runs every step |
| Step 6, before the server applied the update | unchanged | absent | runs every step |
| Step 6, after the server applied the update | `H` | absent | takes the remote repair path and records the rule merge fact once |
| Step 8 | `H` | present, unpublished | takes the publication-only path: publishes the fact and confirms the branch |
| Step 9 | `H` | present, published | takes the publication-only path: confirms the branch |
| A completed run | `H` | present, published | takes the publication-only path again and prints the same output; nothing changes |

The remote repair path applies when the server branch is at the head or
descends from it, the clone holds no merge fact for the candidate, and the
checked-out branch is still at the candidate's base. The command then skips
the check that the checked-out branch equals the hosted tip, evaluates the
rule again on the imported facts, and records the missing fact with `commit`
equal to the head:

```text
origin refs/heads/main already contains 9b2e4c6a8d0f for proposal 1c2d3e4f5a6b
Recorded missing rule merge event 7d8e9f0a1b2c under rule ordinary with 2 evidence item(s)
```

The publication-only path is for the executing actor that signed the rule
merge fact. It applies when your identity is listed in the `actors` of rule
`NAME` in the candidate's base policy, your clone holds a rule merge fact for
the candidate under `NAME` that your identity signed under that policy, and
`REMOTE` is an `hn serve` remote. The command prints the preview, skips the
`proposal is already recorded as merged` refusal and the check that the
checked-out branch equals the hosted tip, publishes your actor chain as
`hn sync` does, and requires the server branch to equal or descend from the
fact's `commit`. It signs nothing, records no fact and sends no branch update:

```text
Publication-only rerun: rule merge event 7d8e9f0a1b2c is already recorded
origin refs/heads/main contains 9b2e4c6a8d0f for proposal 1c2d3e4f5a6b
Rule merge event 7d8e9f0a1b2c under rule ordinary is published on origin
```

When the server branch does not contain the fact's commit, the command still
publishes the fact and then exits 1 with
`rule merge event ID is recorded but REMOTE refs/heads/BRANCH does not contain COMMIT; a publication-only rerun never advances the branch`.

Every other rerun of an already merged candidate is refused with
`automerge blocked: proposal is already recorded as merged`, as before. That
covers a rerun without `--remote`, a rerun by an identity that is not an
executing actor of the rule or that signed no rule merge fact for the
candidate, a candidate merged only by a maintainer's merge fact, and a rule
whose acceptance mode is `maintainers`. The repair of an interrupted
`hn merge` remains for maintainers only.

### A second maintainer runs the command

A second maintainer who runs the command after the first one finished also
takes the step 5 path. If the first maintainer's merge fact has already
reached the second clone, the command reports the branch as advanced and
exits 0. Otherwise the second clone records its own merge fact. Two merge
facts for one candidate from different maintainers are valid. A lineage has
a merge conflict only when two different candidates in it are merged, so
`hn proposal status` still reports the candidate as `merged`.

### Automerge rules

A repository whose policy has [automerge rules](governance-v0.md) can let a
rule's executing actor advance the branch through the server:

```sh
hn automerge PROPOSAL --rule NAME --execute --remote origin
```

`hn automerge` checks the rule first, as it does locally: the checked-out
branch must be the rule's target branch at the proposal's base, and the
proposal's author and changed paths must match the rule. With `--remote` it
then imports the hosted facts with `hn sync` and inspects the rule again, so a
trusted change request or failing run that exists only on the server blocks
it. The saved replication selection for the remote must import every
maintainer, trusted reviewer, protected-check reviewer and trusted runner of
the policy; `--all` and `--all-trusted` do. The import also publishes your
local facts, as `hn sync` always does, even when the rule is then refused. The checked-out branch must equal the hosted tip; otherwise the command
asks you to update it and rerun. Finally it runs the advancement of
`hn merge PROPOSAL --remote REMOTE`, bound to that tip with `hn-expected-tip`
and to the rule's executing actor.

The rule's acceptance mode decides what the advancement asks of the server:

- Under acceptance mode `maintainers`, the client sends the same request as
  `hn merge PROPOSAL --remote REMOTE`. The candidate needs maintainer
  acceptance, and the server applies every check above.
- Under acceptance mode `rule`, the standing rule stands in for maintainer
  acceptance. In step 1 the client evaluates the rule on its imported facts
  and the candidate's base policy. The rule must be satisfied and your
  identity must be one of its executing actors; the acceptance and maintainer
  checks of `hn merge` do not apply. Step 6 adds
  `--push-option=hn-rule=NAME`, and the server evaluates the rule itself, as
  [How the server judges a rule](#how-the-server-judges-a-rule) describes.
  Once the branch is at the head, step 8 evaluates the rule again and your
  client signs a rule merge fact with `commit` equal to the head, `rule` set
  to `NAME`, and the rule's counted approvals and passing results as
  `evidence`. Step 9 publishes it in your actor chain. The server judges the
  fact like any other fact it receives and signs nothing itself.

A rule advancement prints the preview and the output of `hn sync`, followed
by these two lines:

<!-- example: standing-serve-advance -->
```sh
hn automerge sha256:1c2d3e4f... --rule ordinary --execute --remote origin
```

```text
Advanced origin refs/heads/main to 9b2e4c6a8d0f for proposal 1c2d3e4f5a6b
Recorded rule merge event 7d8e9f0a1b2c under rule ordinary with 2 evidence item(s)
```

When the server refuses a rule advancement, the command prints each
`hn-serve/1` line and its sentence without Git's `remote: ` prefix, as
`hn merge --remote` does. It then exits 1 with the branch unchanged and no
merge fact recorded. The three codes the server adds for rules are listed in
[Reason codes for rule advancement](protocol-v0.md#reason-codes-for-rule-advancement).
`protected-rule-veto` names a trusted change request or failure that reached
the server after your import; resolve those events and rerun the command.
`protected-rule-not-satisfied` means the server's evaluation of the rule
found an unmet condition; run the preview, `hn automerge PROPOSAL --rule NAME`,
after `hn sync` to see it. `advance-not-rule-executor` means the rule in the
candidate's base policy does not list your identity in its `actors`. When the
server accepted the push but the branch is not at the head afterwards, the
command names `hn automerge PROPOSAL --rule NAME --execute --remote REMOTE` as
the command to rerun.

Rule advancement needs an `hn serve` that includes standing acceptance. A
server that supports `hn merge --remote` but predates standing acceptance
rejects the `hn-rule` push option with `unsupported-command`. The client then
prints the server's lines and exits 1 with
`REMOTE does not support rule advancement (hn-rule); upgrade hn on the server`,
and the branch does not move. Upgrade `hn` on the server and rerun the
command.

Without `--remote`, `hn automerge --execute` refuses a target branch that
tracks an `hn serve` remote, or a remote it cannot reach to tell, before it
creates a local merge commit or merge fact, because the server never accepts a
local merge commit on a protected branch.

#### How the server judges a rule

An advancement request that carries `hn-rule=NAME` together with `hn-advance`
and `hn-expected-tip` asks the server to accept the candidate under the named
rule in place of maintainer acceptance. The server evaluates the rule itself,
from the candidate's signed base policy and the facts it holds, with the same
derivation `hn automerge` uses in the clone. It adds one check to
[the checks for a protected update](#the-checks-for-a-protected-update),
judges two by the rule and skips one:

- **Step 7a**, after step 7: the destination policy at the tip must be the
  candidate's base policy, compared by digest. A rule applies only under the
  policy that defines it, so when the branch's policy changed after the
  candidate's base, the request is `protected-destination-policy` with
  `missing=proposal` and the next action `revise ID against T`.
- **Step 10**: the rule replaces readiness and maintainer acceptance. The
  request is `protected-rule-not-satisfied` when the base policy has no rule
  with that name, when the rule's acceptance mode is `maintainers`, when the
  rule targets another branch, when the author or a changed path is outside
  the rule, when the candidate changes the policy or a protected-check path,
  or when counted approvals or passing results are below the policy's
  thresholds. The last case names `missing=review`, `missing=ci` or both, and
  the next action is `run hn automerge ID --rule NAME`. A current trusted
  change request or a current trusted failure is `protected-rule-veto`, and
  `ids` names the candidate and then each blocking event.
- **Step 11** does not run. Step 7a already made the destination policy the
  base policy, so step 11 would repeat step 10.
- **Step 13**: the pushing actor must be listed in the rule's `actors` in the
  base policy; otherwise the request is `advance-not-rule-executor`. The
  pushing actor does not need to be a maintainer.

Steps 1 to 9 and step 12 run unchanged, so a current maintainer rejection is
still `protected-blocked` at step 9. The server reads the facts it holds when
the push arrives. A trusted change request or failing run that reaches the
server after `hn automerge` imported the facts and before it pushed therefore
blocks the advancement at step 10:

<!-- example: standing-serve-veto -->
Reviewer `S` requests changes after the executing actor's import (US4-3):

```text
hn-serve/1 reject ref=refs/heads/main actor=<executor> code=protected-rule-veto ids=sha256:<candidate>,sha256:<change request> next="resolve the named events, then retry"
hn-serve: candidate sha256:<candidate> is blocked by rule ordinary: trusted change request sha256:<change request>.
```

The values in angle brackets stand for the executing actor, the candidate and
the change request. Git relays both lines with a `remote: ` prefix.

A direct push and an advancement request without `hn-rule` are judged as
before: they need maintainer acceptance under both policies, whatever
automerge rules the policy has. The server signs nothing and creates no commit
for a rule advancement either. The three reason codes for rule advancement are
listed in
[Reason codes for rule advancement](protocol-v0.md#reason-codes-for-rule-advancement).

### Two advancements at the same time

When two maintainers advance different proposals of one branch at the same
moment, the server applies one of them. The other read the same tip `T` in
step 4, so step 3 of the server's checks refuses it with
`protected-stale-tip` before it reads any policy:

<!-- example: reject-stale-advance -->
The second of two concurrent advancement requests (US3-6):

```text
remote: hn-serve/1 reject ref=refs/heads/main actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=protected-stale-tip ids=3c5e7a9b1d2f4e6a8c0b2d4f6e8a0c1e3f5a7b9d,9b2e4c6a8d0f1e3c5a7b9d1f3e5c7a9b2d4f6e8a next="fetch, then retry or revise"
remote: hn-serve: refs/heads/main moved to 9b2e4c6a8d0f1e3c5a7b9d1f3e5c7a9b2d4f6e8a after this request read 3c5e7a9b1d2f4e6a8c0b2d4f6e8a0c1e3f5a7b9d.
```

`hn merge --remote` prints the same two lines without the `remote: ` prefix.
If the losing command reads the tip after the winner moved it, the server
refuses it with `protected-not-fast-forward` instead. Either way the branch
stays at the winner's head, and the losing author revises the proposal onto
the new tip.

### Merging without a remote

`hn merge PROPOSAL` without `--remote` keeps its existing behavior. It
creates a `--no-ff` merge commit in the current checkout and records a merge
fact for that commit, and it does not contact any remote, including an
`hn serve` remote. `--branch` without `--remote` is a usage error.

## Runners and verifiers

A CI runner executes run requests and publishes signed results. A verifier
checks the evidence for a proposal in its own clone. Both follow a hosted
repository with the all-trusted selection, which imports every new proposal
and run request without naming each actor and candidate. The trust boundary of
that selection is described in
[All-trusted selection for hn serve remotes](replication-v0.md#all-trusted-selection-for-hn-serve-remotes).

### Key bindings for runners and verifiers

The server account accepts SSH connections only from bound keys, so a runner
or a verifier needs a key binding before it can clone or fetch. A runner also
publishes: `hn sync` pushes its actor chain, which carries every `run.result`
it signs, and the server accepts an actor chain only from a key bound to that
actor. Any other key is refused with `actor-key-mismatch`. Bind the runner's
key to the actor that `hn identity show` prints in the runner's clone, as
[Binding and removing keys](#binding-and-removing-keys) describes.

A binding grants no policy role. Readiness counts a result only when its
runner is listed under `trustedRunners` for the pipeline in the base
`.hn/policy.json`, so add the runner's actor there as well.

A verifier with its own Hubnot identity is bound the same way. A verifier
clone without an identity signs nothing and publishes nothing, but it still
needs a bound key to connect. The administrator binds that key to an actor
fingerprint reserved for the verifier.

### Choosing an SSH key per clone

When several participants share one Unix account, as a maintainer, a runner
and a verifier on one build machine do, each clone selects its own key in its
Git configuration:

```sh
git clone -c core.sshCommand="ssh -i ~/.ssh/runner -o IdentitiesOnly=yes" \
  hn@server.example:demo.git runner
```

`git clone -c` saves the setting in the new clone, so later `git fetch` and
`git push` use the same key. `hn sync` and `hn runner` use it too. The clone's
`core.sshCommand`, `ssh.*`, `http.*`, `credential.*` and `protocol.*` settings
apply to the fetch of every selected actor chain, proposal and memory stream,
even though that fetch writes into a temporary quarantine repository instead
of the clone. `GIT_SSH_COMMAND` in the environment still overrides the clone's
setting, as it does for Git. This needs Git 2.31 or later on the client. With
an older Git, export `GIT_SSH_COMMAND` instead. Details are in
[Exact fetch and quarantine lifecycle](replication-v0.md#exact-fetch-and-quarantine-lifecycle).

### Saving the all-trusted selection

Run this once in each runner or verifier clone:

```sh
hn replication select origin --all-trusted
```

The command checks that `origin` advertises the `refs/hn/serve/v1` marker and
refuses an ordinary remote. The selection is saved in the clone, and every
later `hn sync origin`, `hn runner once` and `hn runner watch` uses it. Add
exact `--actor`, `--proposal` or `--memory` selectors to the same command only
when the clone needs something the mode does not discover.

### What each sync imports and validates

Every `hn sync origin` with the all-trusted selection runs these steps:

1. It checks identification again. When `origin` no longer advertises the
   marker, it fetches nothing, prints
   `remote origin no longer identifies as hn serve; reselect with hn replication select`,
   still publishes the clone's own facts and exits 1.
2. It requests every advertised `refs/hn/actors/ACTOR` and
   `refs/hn/proposals/HASH` ref, then each exact selector.
3. It fetches each ref into client quarantine and applies the saved per-ref
   budgets, structural validation, relationship and dependency validation and
   identity continuity. A ref that passes is promoted atomically into
   `refs/hn/remotes/origin/...`.
4. It prints one line per requested ref, such as
   `Replication actor ACTOR: promoted`,
   `Replication proposal ID: promoted` or a `failed (STATUS)` line with a
   diagnostic.
5. It publishes the clone's own actor chain, proposal code refs and memory
   streams.

The server checked every actor chain and proposal ref when it arrived and
refused the ones that failed, so refused facts never appear in the
advertisement. The client checks every fact again itself. A server that
misbehaves can withhold facts from a clone, and it cannot make the clone
accept an event with a broken signature or a broken chain. The marker ref is
never imported.

### Participants who have not published yet

An actor whose key is bound and who has never pushed has no actor ref on the
server. The all-trusted selection requests only advertised refs, so that
actor produces no request and no output line. A clone that also names the
actor with `--actor` next to `--all-trusted` prints
`Replication actor ACTOR: not advertised yet` and still exits 0. Under an
exact selection without `--all-trusted`, the same actor fails as
`dependency-missing` and `hn sync` exits 1.

### Memory streams need exact selection

The all-trusted selection never requests memory refs. Import a memory stream
by naming it next to the mode:

```sh
hn replication select origin --all-trusted --memory sha256:STREAM
```

An exact memory selector that the server does not advertise fails as
`dependency-missing`.

### Running CI requests

`hn runner once` synchronizes, executes the first pending request for one
pipeline signed by one requester, records a signed result and synchronizes
again to publish it:

```sh
hn runner once --accept-pipeline test --accept-actor MAINTAINER
```

```text
Runner accepted request 1e2822d10cd6 from 9d71a3cd9c0a for pipeline test
Runner recorded passed result 9a34c097bf6b with sandbox backend
```

`--accept-actor` takes the requester's full actor fingerprint, usually a
maintainer's, because readiness counts a result only when its run request was
signed by a policy maintainer or by an actor that the pipeline's `requesters`
list names. When nothing is pending, the command prints
`No pending test requests from actor 9d71a3cd9c0a.` and exits 0.

Repeat `--accept-actor` to serve several requesters from one runner, for
example a maintainer and an orchestrator listed in `pipelines.test.requesters`:

```sh
hn runner once --accept-pipeline test --accept-actor MAINTAINER --accept-actor ORCHESTRATOR
```

The runner accepts 1 to 64 distinct full fingerprints and refuses a duplicate
or malformed value before it synchronizes. Each invocation still executes at
most one request, signed by any listed actor. With more than one actor, the
runner also checks the base policy of the requested proposal and executes a
request only when its signer is a maintainer or a listed requester of the
pipeline. It skips any other request with
`hn runner: skipped REQUEST: signer ACTOR is neither a maintainer nor a requester of pipeline test under the base policy`
on standard error and leaves it unexecuted. The idle message names every
actor: `No pending test requests from actors 9d71a3cd9c0a, 5be0c1f2a7d4.` A
single `--accept-actor` keeps its earlier behavior and executes every pending
request that its actor signs.

The default
`--backend sandbox` runs the steps under Bubblewrap. On a host without
Bubblewrap, `--backend host --allow-unsafe-host-execution` runs them directly
on the runner's host, which is safe only for proposals the runner's operator
trusts.

`hn runner watch` takes the same flags and repeats the cycle until it is
interrupted. It waits `--interval` between cycles that ran nothing; the
default is 30 seconds and the minimum is 1 second.

Each cycle starts with `hn sync`, and a failing import stops the cycle before
any request runs. Under the all-trusted selection a participant who has not
published yet causes no failure, so new participants do not stop CI.

### Verifying a hosted repository from a fresh clone

A verifier needs only Git, `hn` and a bound key:

```sh
git clone ssh://hn-serve@git.example.internal/pingpong.git verify && cd verify
hn replication select origin --all-trusted
hn sync origin
hn proposal status sha256:1c2d3e4f...
```

The clone has no Hubnot identity. `hn proposal status` recomputes the result
from the events the clone verified itself, under the proposal's base policy:
the signed head, the trusted approvals, the trusted CI passes, the acceptance
decisions and, after an advancement, `Status:   merged`. No server verdict is
read. `hn issue show ISSUE` shows the state of an issue the same way.

### End-to-end team flow

This is the Phase 0 flow of the rust-pingpong project with five participants:
a maintainer, an orchestrator, an implementer, a reviewer and a runner. Each
one has a clone, an identity from `hn init`, a bound key and the saved
`hn replication select origin --all-trusted`. The base policy requires one
trusted approval, one passing `test` result from the runner and one
maintainer acceptance.

1. The orchestrator opens an issue:
   `hn issue open --body "Serve the ball and answer with pong." "Serve the ball"`,
   then `hn sync origin`.
2. The implementer runs `hn sync origin` and reads the issue with
   `hn issue show ISSUE --json`.
3. The implementer runs `git switch -c feature/serve-ball`, commits the
   change, runs `git push -u origin feature/serve-ball`, opens the proposal with
   `hn proposal open --base main --head feature/serve-ball "Serve the ball"`
   and runs `hn sync origin`.
4. The maintainer runs `hn sync origin`, `hn run request PROPOSAL test` and
   `hn sync origin`.
5. The runner runs `hn runner once --accept-pipeline test --accept-actor MAINTAINER`
   and `hn sync origin`.
6. The reviewer runs `hn sync origin`,
   `hn review PROPOSAL --approve --body "pingpong.sh answers pong."` and
   `hn sync origin`.
7. The maintainer runs `hn sync origin`, `hn decide PROPOSAL --accept` and
   `hn sync origin`, then advances `main` with
   `hn merge PROPOSAL --remote origin`.
8. The orchestrator runs `hn sync origin`, reads the issue head from
   `head_ids` in `hn issue show ISSUE --json`, closes the issue with
   `hn issue close ISSUE --expect HEAD` and runs `hn sync origin`.
9. Anyone runs the verifier recipe above and sees the proposal `merged` and
   the issue closed.

No participant names an actor or a proposal in a selection, and no
participant pushes `main`. The server moves `main` once, when the
maintainer's `hn merge --remote` requests the advancement.
`serve_replication_test.go` runs this flow on every test run with a portable
shell pipeline in place of the project's cargo pipeline.

### Evidence that depends on the host

Three tests measure or enforce properties that depend on the test host, and
each one logs what it saw:

- `TestServeQualityPushVerdictTimeNFR001` builds a hosted repository with
  1,000 events from four actors, restores it before each of 20 timed pushes
  of 50 events and a protected `main` update, logs every duration and fails
  when the 95th percentile is 5 seconds or more. The server-side `hn` binary
  is built without the race detector. The test skips under `go test -short`.
- `TestServeQualityEnforcedWriteBoundary` runs a full acceptance run with
  every server-side process, administration commands included, inside a
  bubblewrap sandbox in which only `$HOME/.hn-serve` and `$HOME/.ssh` are
  writable, after checking that the sandbox refuses writes to `$HOME`, `/tmp`
  and another absolute path. Without bubblewrap or unprivileged user
  namespaces it skips with the reason, and `TestServeQualityWrittenPathsAndModes`
  remains as snapshot evidence of the same rule.
- `TestServeSSHDRoundTrip` starts an unprivileged OpenSSH server on
  `127.0.0.1` with the generated `authorized_keys`, clones, pushes a feature
  branch, has a direct `main` push rejected, and checks that `restrict` refuses
  a terminal and local port forwarding. It skips with the reason when `sshd`,
  `ssh` or `ssh-keygen` is missing, when it runs as uid 0, or when `sshd` does
  not start, and it includes the `sshd` log in the skip message.

The LFS tests that drive the real Git LFS client (`TestServeLFSRoundTrip`,
`TestServeLFSDocumentedExample`, `TestServeLFSWrittenPathsAndModes`,
`TestServeLFSEnforcedWriteBoundary` and the client part of
`TestServeLFSLockingUnsupported`) skip with the reason when `git lfs version`
fails. `TestServeLFSEnforcedWriteBoundary` also skips under the same conditions
as `TestServeQualityEnforcedWriteBoundary`. The other LFS tests speak the
protocol directly and need no client.

## Large files with Git LFS

A hosted repository can store Git LFS objects next to its Git history. Clients
transfer them over the same SSH login and forced command as `git fetch` and
`git push`, using the `git-lfs-transfer` protocol, version 1, from the Git LFS
[SSH adapter proposal](https://github.com/git-lfs/git-lfs/blob/main/docs/proposals/ssh_adapter.md).
The server opens no HTTP port, and LFS sessions check the key and the
repository name exactly as Git sessions do.

### What a client needs

Each participant needs Git LFS 3.0 or later. Since 3.0, Git LFS tries
`git-lfs-transfer` over SSH first for an SSH remote
([Git LFS changelog, 3.0.0](https://github.com/git-lfs/git-lfs/blob/main/CHANGELOG.md#300-24-sep-2021)).
The client behavior this section describes is that of Git LFS 3.7.1, the
version the tests ran against. A clone of a hosted repository uses LFS the
usual way:

```sh
git clone hn@server.example:demo.git
cd demo
git lfs install --local
git lfs track '*.bin'
git add .gitattributes model.bin
git commit -m 'Add the model'
git push origin HEAD:refs/heads/feature/model
```

Git LFS starts its own SSH connection with `git-lfs-transfer 'demo.git' upload`
or `download`. By default it asks OpenSSH to multiplex its connections. When
that causes problems, for example with a wrapper around `ssh` that does not
support multiplexing, turn it off in the clone:

```sh
git config lfs.ssh.automultiplex false
```

Without multiplexing, Git LFS transfers one object at a time over one
connection
([`tq/manifest.go`](https://github.com/git-lfs/git-lfs/blob/v3.7.1/tq/manifest.go)).
A second participant who clones before configuring LFS receives pointer files;
`git lfs install --local` followed by `git lfs pull` downloads the content.

### What the server stores

Each repository's objects live below `state/repos/NAME/lfs/`, which the first
LFS session creates with mode 0700:

- `lfs/incoming/` holds uploads in progress, one file per upload with a random
  name and mode 0600.
- `lfs/objects/OID[0:2]/OID[2:4]/OID` holds each stored object with mode 0600.
  The object ID is the SHA-256 of the content, as 64 lowercase hexadecimal
  digits.

An upload streams into `lfs/incoming/`. After the last byte, the server checks
that the byte count equals the size the client declared and that the SHA-256
of the content equals the object ID. Only then, and only after the quota check
described below, does it rename the file into `lfs/objects/` and `fsync` the
file and its directories. A download can therefore only ever return verified
content. A stored object is never replaced, and the server writes nothing to
disk for an upload of an object that is already stored. It hashes that
upload's data in memory and drops it, reading at most the smaller of the
declared size and the stored size plus one byte. When the data matches the
stored object, the upload succeeds and costs no quota. Any other data gets the
`lfs-object-mismatch` answer described below, and data past that bound also
ends the session.

When the content does not match, the server removes the staged file and
answers status 422 with an `lfs-object-mismatch` rejection line naming the
object ID, which the client shows as the reason for the failed upload:

<!-- example: lfs-object-mismatch -->
```text
hn-serve/1 reject ref=- actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=lfs-object-mismatch ids=6a1e5e2f0c9d4b3a8f7e6d5c4b3a2f1e0d9c8b7a6f5e4d3c2b1a0f9e8d7c6b5a next="retry the upload"
```

The server reads at most the declared size of an upload plus one byte of
object data. It reads each data packet only up to the bytes the declared
size still allows, so when a packet goes past that size, the server reads
one byte beyond the size from it and stops there. It removes the staged file
and sends the same `lfs-object-mismatch` answer. The rest of the object is
left unread, so the session ends there with exit status 1. A client
therefore cannot make the server read more than the declared size plus one
byte of object data, however large its packets are. A `put-object` request
without a valid object ID or `size=` argument has no such bound, so the
server answers status 400 and ends the session without reading its data.

### The LFS quota

Every repository has an LFS quota in bytes, set with `--lfs-quota` on
`hn serve repo create` or `hn serve repo set` and 1073741824 bytes (1 GiB) by
default. Stored bytes are the sum of the object sizes in `lfs/objects/`, which
`hn serve repo show NAME` prints as `lfs-stored:`. Uploads in progress never
count. The quota is inclusive: with a quota of 1010 bytes and 1000 bytes
stored, a 10-byte object is accepted and an 11-byte object is refused.

The server checks the quota three times for each upload, so an object that
would exceed it never becomes downloadable:

1. When the client asks which objects to upload, the server adds the declared
   sizes of every requested object that is not stored yet. If the total would
   exceed the quota, it refuses the whole request with status 507.
2. Before it reads an object's data, it checks the declared size the same way,
   and on refusal reads and discards the data, up to the declared size plus
   one byte. An object that is already stored skips this check, because its
   upload is never staged or stored again.
3. After verifying the content, it takes the repository's `lfs.lock`, counts
   the stored bytes again and renames the object into place only if it still
   fits. Two uploads that each fit alone cannot exceed the quota together.

LFS sessions never take the repository lock that pushes hold. They take
`lfs.lock` only for that last step, so a long upload does not hold up other
uploads or any push. A refusal
carries an `lfs-quota` rejection line with `budget=lfs-quota`, the quota as
`limit` and, as `measured`, the stored bytes the upload would have produced.
Git LFS 3.7.1 stops the push before any ref moves, and `git push` exits with
status 1:

<!-- example: lfs-quota -->
```text
LFS: batch response: status 507 from server (hn-serve/1 reject ref=- actor=4f1c9a6d0d2b7e3a8c5f6e1b9d0a7c3e2f4b6d8a0c1e3f5a7b9d1c3e5f7a9b1c code=lfs-quota budget=lfs-quota limit=100 measured=150 next="ask the administrator to raise the quota")
error: failed to push some refs to 'ssh://server.example/demo.git'
```

To accept the upload, the administrator raises the quota and the participant
pushes again:

```sh
sudo -u hn-serve hn serve repo set demo --lfs-quota 2147483648
```

### Interrupted uploads

An upload that stops before its last byte never reaches `lfs/objects/`, so it
is never downloadable and never counted. When the connection closes, the
session removes the staged file itself. When the session is killed outright,
the file stays in `lfs/incoming/`; at the start of every LFS session for the
repository, the server removes staged files older than one hour. Younger files
stay because they may belong to an upload that is still running.

### Locking and requests the server does not offer

The server does not implement file locking. It never advertises the `locking`
capability, and it answers `lock`, `unlock` and `list-lock` with status 501 and
the message `locking is unsupported by hn serve`. Git LFS 3.7.1 asks for the
lock list before each push anyway; after the 501 answer it records
`lfs.<url>.locksverify false` in the clone's configuration and carries on.
`git lfs lock FILE` and `git lfs locks` exit with status 2 and show the
server's message.

`git-lfs-authenticate`, which older clients use to obtain credentials for an
HTTPS LFS endpoint, is refused with `unsupported-command`, as described in
[Requests the server accepts](#requests-the-server-accepts). There is no HTTPS
LFS endpoint.

### Protocol answers

Each request in an LFS session gets one of these statuses. Statuses 400, 404,
422, 501, 503 and 507 carry one message line, which the Git LFS client shows.

| Status | When |
|----|----|
| 200 | The request succeeded |
| 400 | An unsupported protocol version, `hash-algo` other than `sha256`, an object ID that is not 64 lowercase hexadecimal digits, or a missing or malformed size. A malformed pkt-line, an unknown command, a `put-object` without a valid object ID or size, or `get-object` in an upload session or `put-object` and `verify-object` in a download session also end the session with exit status 1 |
| 404 | `get-object` or `verify-object` for an object that is not stored, or stored with a different size |
| 422 | Uploaded content does not match its object ID or declared size (`lfs-object-mismatch`). Data that goes past the declared size also ends the session with exit status 1 |
| 501 | `lock`, `unlock` or `list-lock` |
| 503 | `lfs.lock` stayed busy for 30 seconds; retry the upload |
| 507 | The upload would exceed the quota (`lfs-quota`) |

A pkt-line length header may not exceed 65519, the limit the proposal sets,
and the server refuses a longer header before reading the packet.
