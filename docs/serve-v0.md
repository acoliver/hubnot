# hn serve v0: governed local Git hosting

## Overview

`hn serve` turns an unprivileged Unix account into a Git host for Hubnot
repositories. OpenSSH authenticates each connection and runs a forced `hn serve`
command, which maps the SSH key to a Hubnot actor and checks every pushed ref
update before Git moves it. The service is optional: no other `hn` command
depends on it, and clients that push to ordinary Git remotes see no change. The
replication rules it reuses are described in
[replication-v0.md](replication-v0.md), and the trust boundaries in
[threat-model.md](threat-model.md).

## Server account and state layout

Run `hn serve` as a dedicated, unprivileged user, for example one created with
`useradd --create-home --shell /bin/sh hn`. All server state belongs to that
account and lives in its home directory. `hn serve` writes only below
`$HOME/.hn-serve/` and to `$HOME/.ssh/authorized_keys`.

Every `hn serve` command checks the effective user ID before it reads `HOME` or
any file. When the command runs as root it stops with:

```text
hn: hn serve refuses to run as root; create an unprivileged user for the server
```

The server home has one fixed layout:

```text
$HOME/
├── .ssh/                       0700, created if absent
│   └── authorized_keys         0600; managed block plus administrator lines
└── .hn-serve/                  0700
    ├── hooks/                  0700, regenerated by every administration command
    │   ├── pre-receive         0700 script: exec ABS_HN serve hook pre-receive
    │   └── post-receive        0700 script: exec ABS_HN serve hook post-receive
    ├── repositories/           0700
    │   └── NAME.git/           bare repository created by hn serve repo create
    └── state/                  0700
        ├── registry.json       0600
        ├── tmp/                0700, TMPDIR for Git and hooks
        └── repos/              0700
            └── NAME/           0700
                ├── config.json     0600
                ├── branches.json   0600, absent until the first owned branch
                ├── push.log        0600, append-only JSON Lines
                ├── lock            0600, flock target for pushes
                ├── lfs.lock        0600, flock target for LFS commits
                └── lfs/            0700
                    ├── incoming/   0700, staged uploads
                    └── objects/    0700, verified objects in OID[0:2]/OID[2:4]/OID
```

`registry.json` binds SSH key fingerprints to actors. `config.json` holds one
hosted repository's protected branches, LFS quota and push budgets.
`branches.json` records which actor created each ordinary branch. `push.log`
records one JSON object per push for operators; the server never reads it back.
The exact file formats are in the
[server-state contract](../kitty-specs/hn-serve-01M5P0NP/contracts/server-state.md).

A repository name starts with a letter or digit, continues with letters,
digits, `.`, `_` or `-`, is at most 100 characters long, never contains `..` and
never ends in `.git`. The bare repository for `NAME` is always
`repositories/NAME.git`.

### What makes the server refuse to run

Each `hn serve` command validates the whole layout before it does anything else.
The first defect stops the command with a message that names the path, in the
form `hn: hn serve state defect: PATH: REASON`. Validation walks names in sorted
order, so the same defect always produces the same message. The server refuses
to run when it finds any of the following:

- a symbolic link anywhere in the layout, including a symlinked `.ssh`
  directory or a symlinked `repositories/NAME.git`;
- a directory whose mode is not 0700, or a state file whose mode is not 0600
  (hook scripts must be 0700); the message reports the observed mode;
- an entry the layout does not define in `.hn-serve/`, `hooks/`, `state/`,
  `state/repos/`, `state/repos/NAME/` or `lfs/`, or an entry in
  `repositories/` that is not `NAME.git` for a valid name;
- a `state/repos/NAME/` without a matching `repositories/NAME.git/`, or the
  reverse;
- a missing `config.json` for a hosted repository;
- a JSON state file with an unknown field, trailing data, a value that breaks
  its rules, or a size above 16 MiB;
- a `push.log` above 64 MiB;
- a hook script that is missing or whose bytes differ from the generated
  script;
- inside `state/tmp/`, `lfs/incoming/` and `lfs/objects/`, any symbolic link,
  device, socket or named pipe, any directory that is not 0700, any file that is
  not 0600, or more than 100,000 entries in one of those subtrees.

The checks inside `state/tmp/` and the LFS directories do not read file
contents or apply name rules, because those directories hold transient and
content-addressed files. Administration commands may keep their own lock files
in `state/tmp/`.

An interrupted state write can leave a temporary file such as
`state/.hn-private-1234` behind. Validation reports it as an unexpected entry;
remove it and rerun the command. The push log grows by one line per push. Archive
or truncate it before it reaches 64 MiB.

### Administration commands and sessions

Administration commands (`hn serve repo ...` and `hn serve key ...`) create any
missing directory in the layout with mode 0700, then rewrite both hook scripts
for the `hn` binary that is running, then validate. Session commands
(`hn serve git` and the internal `hn serve hook`) only read: a missing directory
or a stale hook script makes them refuse.

Each hook script is two lines that run the absolute, symlink-resolved path of the
`hn` binary:

```sh
#!/bin/sh
exec /usr/local/bin/hn serve hook pre-receive
```

After you move or upgrade `hn`, run any `hn serve repo` or `hn serve key`
command to regenerate the hooks and the `authorized_keys` block. Until then,
every fetch and push refuses with a hook-script defect. `hn` refuses to write hooks when its
own path contains a quote, a backslash, whitespace or a control character,
because the same path is written unquoted into `authorized_keys`; install `hn`
at a path without them.

### Protected branch order in config.json

The `protected` list in `config.json` names full refs such as
`refs/heads/main`. Its first entry is the default protected branch, and the
repository's `HEAD` points to it. The remaining entries follow in byte order
with no duplicates. For example, a repository whose default branch is `trunk`
and which also protects `alpha` and `release` stores
`["refs/heads/trunk", "refs/heads/alpha", "refs/heads/release"]`.

### Locks and filesystems

Pushes to one repository are serialized with `flock(2)` on
`state/repos/NAME/lock`, and a push waits up to 120 seconds for it. `flock` is
not reliable on every network filesystem, so keep the server home on a local
filesystem.
