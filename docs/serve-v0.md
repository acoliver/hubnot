# hn serve v0: governed local Git hosting

## Overview

`hn serve` turns an unprivileged Unix account into a Git host for Hubnot
repositories. OpenSSH authenticates each connection and runs a forced `hn serve`
command, which maps the SSH key to a Hubnot actor and checks every pushed ref
update before Git moves it. The service is optional: no other `hn` command
depends on it, and clients that push to ordinary Git remotes see no change. The
replication rules it reuses are described in
[replication-v0.md](replication-v0.md), and the trust boundaries in
[threat-model.md](threat-model.md).

## Server account and state layout

Run `hn serve` as a dedicated, unprivileged user, for example one created with
`useradd --create-home --shell /bin/sh hn`. All server state belongs to that
account and lives in its home directory. `hn serve` writes only below
`$HOME/.hn-serve/` and to `$HOME/.ssh/authorized_keys`.

Every `hn serve` command checks the effective user ID before it reads `HOME` or
any file. When the command runs as root it stops with:

```text
hn: hn serve refuses to run as root; create an unprivileged user for the server
```

The server home has one fixed layout:

```text
$HOME/
├── .ssh/                       0700, created if absent
│   └── authorized_keys         0600; managed block plus administrator lines
└── .hn-serve/                  0700
    ├── hooks/                  0700, regenerated by every administration command
    │   ├── pre-receive         0700 script: exec ABS_HN serve hook pre-receive
    │   └── post-receive        0700 script: exec ABS_HN serve hook post-receive
    ├── repositories/           0700
    │   └── NAME.git/           bare repository created by hn serve repo create
    └── state/                  0700
        ├── registry.json       0600
        ├── tmp/                0700, TMPDIR for Git and hooks
        └── repos/              0700
            └── NAME/           0700
                ├── config.json     0600
                ├── branches.json   0600, absent until the first owned branch
                ├── push.log        0600, append-only JSON Lines
                ├── lock            0600, flock target for pushes
                ├── lfs.lock        0600, flock target for LFS commits
                └── lfs/            0700
                    ├── incoming/   0700, staged uploads
                    └── objects/    0700, verified objects in OID[0:2]/OID[2:4]/OID
```

`registry.json` binds SSH key fingerprints to actors. `config.json` holds one
hosted repository's protected branches, LFS quota and push budgets.
`branches.json` records which actor created each ordinary branch. `push.log`
records one JSON object per push for operators; the server never reads it back.
The exact file formats are in the
[server-state contract](../kitty-specs/hn-serve-01M5P0NP/contracts/server-state.md).

A repository name starts with a letter or digit, continues with letters,
digits, `.`, `_` or `-`, is at most 100 characters long, never contains `..` and
never ends in `.git`. The bare repository for `NAME` is always
`repositories/NAME.git`.

### What makes the server refuse to run

Each `hn serve` command validates the whole layout before it does anything else.
The first defect stops the command with a message that names the path, in the
form `hn: hn serve state defect: PATH: REASON`. Validation walks names in sorted
order, so the same defect always produces the same message. The server refuses
to run when it finds any of the following:

- a symbolic link anywhere in the layout, including a symlinked `.ssh`
  directory or a symlinked `repositories/NAME.git`;
- a directory whose mode is not 0700, or a state file whose mode is not 0600
  (hook scripts must be 0700); the message reports the observed mode. This
  includes each `repositories/NAME.git` directory itself. Validation does not
  look inside a bare repository, but its top directory must be 0700;
- an entry the layout does not define in `.hn-serve/`, `hooks/`, `state/`,
  `state/repos/`, `state/repos/NAME/` or `lfs/`, or an entry in
  `repositories/` that is not `NAME.git` for a valid name;
- a `state/repos/NAME/` without a matching `repositories/NAME.git/`, or the
  reverse;
- a missing `config.json` for a hosted repository;
- a JSON state file with an unknown field, trailing data, a value that breaks
  its rules, or a size above 16 MiB;
- a `push.log` above 64 MiB;
- a hook script that is missing or whose bytes differ from the generated
  script;
- inside `state/tmp/`, `lfs/incoming/` and `lfs/objects/`, any symbolic link,
  device, socket or named pipe, any directory that is not 0700, any file that is
  not 0600, or more than 100,000 entries in one of those subtrees.

The checks inside `state/tmp/` and the LFS directories do not read file
contents or apply name rules, because those directories hold transient and
content-addressed files. Administration commands may keep their own lock files
in `state/tmp/`.

An interrupted state write can leave a temporary file such as
`state/.hn-private-1234` behind. Validation reports it as an unexpected entry;
remove it and rerun the command. An administration command that stops while it
rewrites a hook can leave a staging file such as `hooks/.hn-hook-1234`.
Validation reports it as an abandoned hook staging file; remove it, then run any
`hn serve repo` or `hn serve key` command to regenerate the hooks. The push log grows by one line per push. Archive
or truncate it before it reaches 64 MiB.

### Administration commands and sessions

Administration commands (`hn serve repo ...` and `hn serve key ...`) create any
missing directory in the layout with mode 0700, then rewrite both hook scripts
for the `hn` binary that is running, then validate. Every one of them does this,
including the read-only `hn serve repo list`, `hn serve repo show NAME` and
`hn serve key list`, so running `hn serve repo list` is a quick way to prepare a
new server account and to check an existing one. Session commands
(`hn serve git` and the internal `hn serve hook`) only read: a missing directory
or a stale hook script makes them refuse.

Each hook script is two lines that run the absolute, symlink-resolved path of the
`hn` binary:

```sh
#!/bin/sh
exec /usr/local/bin/hn serve hook pre-receive
```

After you move or upgrade `hn`, run any `hn serve repo` or `hn serve key`
command to regenerate the hooks and the `authorized_keys` block. Until then,
every fetch and push refuses with a hook-script defect.

### Concurrent commands

Many `hn serve` commands can run at once, for example several pushes and an
administrator's `hn serve repo list`. They coordinate through an `flock(2)` lock
on the `.hn-serve` directory itself, so the layout gains no extra file.
An administration command holds the lock exclusively while it rewrites the hooks
and validates the layout. A session command holds it shared while it validates,
so sessions run side by side and never see a hook script half written. Each
command releases the lock after validation, before it does its own work. A
command that cannot get the lock within 120 seconds stops with
`hn: hn serve layout is busy: ...`; run it again when the other command
finishes.

The hook scripts and `authorized_keys` contain the `hn` path without quotes, and
`/bin/sh` runs the hooks. `hn` therefore accepts only a clean absolute path made
of ASCII letters, digits and the characters `/ . _ - + @ , :`, none of which the
shell expands or splits. Any other character, such as `$`, a backtick, `;`, `*`,
a quote, a backslash, whitespace or a non-ASCII letter, makes every
administration command refuse before it writes a hook. Install `hn` at a path
such as `/usr/local/bin/hn` or `/home/hn/bin/hn`.

### Protected branch order in config.json

The `protected` list in `config.json` names full refs such as
`refs/heads/main`. Its first entry is the default protected branch, and the
repository's `HEAD` points to it. The remaining entries follow in byte order
with no duplicates. For example, a repository whose default branch is `trunk`
and which also protects `alpha` and `release` stores
`["refs/heads/trunk", "refs/heads/alpha", "refs/heads/release"]`.

### Locks and filesystems

Pushes to one repository are serialized with `flock(2)` on
`state/repos/NAME/lock`, and a push waits up to 120 seconds for it.
`hn serve repo lock-exec NAME -- COMMAND [ARG]...` takes the same lock, runs
`COMMAND` without a shell in the bare repository with `GIT_DIR` set to it,
releases the lock and exits with the command's status. When the lock stays busy
for the whole wait it exits 1 with a `repository-busy` message. `flock` is
not reliable on every network filesystem, so keep the server home on a local
filesystem.

## Key bindings and authorized_keys

OpenSSH authenticates every connection to the server account. `hn serve` does
not implement SSH; it decides which Hubnot actor an authenticated key belongs
to and makes sure OpenSSH runs `hn serve git` for that key and nothing else.

### What a key binding is

A key binding maps one SSH public key, identified by its full SHA256
fingerprint, to one Hubnot actor, identified by its full 64-hex actor
fingerprint. Bindings are stored in `state/registry.json`. One key binds to
exactly one actor. One actor may hold several keys, for example one per
laptop or one per security key.

A binding gives the actor two things: SSH access to the hosted repositories
and attribution of that actor's pushes. It grants no policy role. Roles such as
maintainer or verifier come only from the policy documents in each repository,
and a push from a bound key is checked against those policies like any other
(C-006).

The [Administering hosted repositories](#administering-hosted-repositories)
section shows the `hn serve key` commands that add, list and remove bindings.

### Supported key types

`hn serve` accepts these OpenSSH public key types:

- `ssh-ed25519`
- `sk-ssh-ed25519@openssh.com`
- `ecdsa-sha2-nistp256`
- `ecdsa-sha2-nistp384`
- `ecdsa-sha2-nistp521`
- `sk-ecdsa-sha2-nistp256@openssh.com`
- `ssh-rsa`

Any other type, including `ssh-dss` and every certificate type, is refused with
a message that names it.

A key is given as one line in the format of a `.pub` file or an
`authorized_keys` entry: the key type, the base64 key and an optional comment,
separated by spaces. A leading `authorized_keys` options field such as
`restrict,command="a b"` is accepted and ignored. Only the key type and base64
key are stored and written back, so options and comments from the input never
reach the server's `authorized_keys`. The line is refused when it is empty,
longer than 16 KiB, contains a tab or any other control character apart from a
single final newline, uses base64 without its `=` padding, or holds a key blob
whose embedded type differs from the type field, whose lengths run past its
end, or that carries trailing bytes.

### Fingerprints

A fingerprint is `SHA256:` followed by 43 characters of unpadded standard
base64: the SHA-256 digest of the decoded key blob. It is the value that
`ssh-keygen -l -E sha256 -f KEY.pub` prints in its second field:

```console
$ ssh-keygen -l -E sha256 -f ~/.ssh/id_ed25519.pub
256 SHA256:Mnm7DCteTtegvPg/NcGZVvsMTFM5gR+dbIBbGci5vSg alice@laptop (ED25519)
```

Every `hn serve` command that takes a fingerprint requires all 43 characters.
A shortened or otherwise malformed fingerprint is refused.

### The managed block in authorized_keys

`hn serve` writes one managed block into `$HOME/.ssh/authorized_keys` of the
server account. The block starts and ends with fixed marker lines and holds one
entry per binding, sorted by fingerprint:

```text
# BEGIN hn serve managed keys; edit with hn serve key
restrict,command="/usr/local/bin/hn serve git --key SHA256:Mnm7DCteTtegvPg/NcGZVvsMTFM5gR+dbIBbGci5vSg" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAICqPfpPz/R1uz/vd9nUpjEhAMWYVmeerTHMSJDGYgg3A hn-serve:4f1c9a6d0d2b
# END hn serve managed keys
```

Each entry has three parts:

- `restrict` turns off port, agent and X11 forwarding, PTY allocation and
  `~/.ssh/rc`;
- `command="ABS_HN serve git --key FINGERPRINT"` makes `sshd` run `hn serve git`
  with the binding's fingerprint whatever command the client asked for.
  `ABS_HN` is the absolute, symlink-resolved path of the `hn` binary that wrote
  the block. The same path rules apply as for the hook scripts, so a path with a
  quote, a backslash or whitespace is refused before anything is written;
- the key type and base64 key, followed by the comment `hn-serve:` and the
  first 12 characters of the bound actor.

A registry with no bindings still produces the two marker lines. Before it
writes an entry, `hn serve` parses the stored public key again and requires its
fingerprint to equal the binding's fingerprint, so a hand-edited registry whose
key and fingerprint disagree stops the command.

Do not edit the block by hand. Every `hn serve key` command rewrites it from
the registry, and so does every `hn serve repo` command. After you move or
upgrade `hn`, run one of them to update the command path.

### Lines outside the block

You can keep your own keys and comments in the same file. `hn serve` changes
only the lines from the begin marker through the end marker. Every byte outside
the block stays as it was, including Windows `
` line endings and a missing
final newline. When the file has no block yet, `hn serve` appends one at the
end, first adding a single `
` if the file does not already end with one. A
marker counts only when it is the whole line, without leading or trailing
spaces.

The new file is written to a temporary file in `.ssh` with mode 0600, synced
and renamed over `authorized_keys`, so `sshd` sees either the old file or the
new one. If a command is interrupted between those steps, a file such as
`.ssh/.hn-private-1234` may be left behind; remove it.

### When hn serve refuses to touch authorized_keys

`hn serve` creates `$HOME/.ssh` with mode 0700 when it does not exist. It stops
before writing anything when it finds any of the following:

- `.ssh` is a symbolic link or is not a directory;
- `.ssh` is writable by group or others, for example mode 0775;
- `authorized_keys` is a symbolic link or is not a regular file;
- `authorized_keys` is writable by group or others, for example mode 0664;
- `authorized_keys` is larger than 4 MiB;
- `authorized_keys` has two begin markers, two end markers, an end marker
  without a begin marker before it, or a begin marker without an end marker
  after it.

The message names the path and, for a mode problem, the command that fixes it,
such as `chmod 700 /home/hn/.ssh`. `hn serve` never repairs an unsafe `.ssh`
or `authorized_keys` itself, because `sshd` with `StrictModes` rejects the same
setup and a silent repair would hide the misconfiguration. An existing `.ssh`
with a safe mode such as 0755 is kept as it is. The rewritten
`authorized_keys` always has mode 0600.
